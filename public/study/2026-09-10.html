复习 1｜线程池生产事故

先回答：为什么“大队列 + 小 corePoolSize”可能让 maximumPoolSize 几乎发挥不了作用？

答完后展开

ThreadPoolExecutor 在达到 corePoolSize 后优先入队，只有队列无法继续接收任务时才扩到 maximumPoolSize。队列过大时，任务可能长期排队，表现为 queue wait time 与 p95/p99 延迟上升。

面试口述版：线程池调优不能只看 maximumPoolSize。core 满后任务先入队，因此过大的队列会把压力隐藏成排队延迟，让 max 很难生效；应结合下游容量、队列等待时间、拒绝数和尾延迟调整，并做业务线程池隔离。

复习 2｜JVM 是什么

先回答：为什么 Java 能做到“一次编译、多平台运行”？JVM 本身是不是完全跨平台？

答完后展开

Java 源码编译为相对平台中立的字节码，每个平台提供自己的 JVM 实现来执行同一套字节码。JVM 实现本身仍依赖具体 OS/CPU。

面试口述版：Java 的跨平台核心是字节码跨平台，而不是 JVM 二进制本身跨平台。不同 OS/CPU 提供对应 JVM 实现来执行相同字节码。

复习 3｜JVM 运行时数据区域

先回答：程序计数器、虚拟机栈、本地方法栈、堆、方法区中，哪些主要是线程私有，哪些共享？

答完后展开

程序计数器、虚拟机栈、本地方法栈主要线程私有；堆和方法区线程共享。方法区是 JVM 规范层面的逻辑概念，HotSpot JDK 8+ 的类元数据主要由 Metaspace 承载。

复习 4｜Agent 技术趋势

先回答：近一年 Agent 工程化最值得关注的三个方向是什么？

答完后展开

可以概括为：编码 Agent 从补全走向长任务执行；工具互操作与 Agent 编排能力继续标准化；企业部署越来越重视权限、Trace、Evaluation、成本和治理，而不只比较模型效果。

复习 5｜LangChain 生态

先回答：LangChain、LangGraph、LangSmith 各自更偏哪一层？Java 项目如何映射？

答完后展开

LangChain 偏 LLM 应用抽象，LangGraph 偏有状态 Agent Workflow，LangSmith 偏 Trace/Evaluation。Java 侧可用 Spring AI 承担 Model/RAG/Tool/Memory/MCP，再由 Spring Service/Workflow 管理复杂业务状态。

间隔复习｜约 3 天前：ThreadLocal

ThreadLocalMap 的 Key 是弱引用，为什么 Value 仍可能滞留？

答完后展开

GC 可以让 Entry 的 key 变 null，但 value 仍被 Entry 强引用；如果线程池线程长期存活且没有 remove，stale entry 可能持续存在并造成上下文污染。

间隔复习｜约 7 天前：Java 泛型

为什么 List<String> 不是 List<Object> 的子类型？PECS 又解决什么问题？

答完后展开

Java 泛型默认是不变的。PECS 用通配符表达读写边界：Producer Extends，Consumer Super；读取 Number 子类型集合可用 ? extends Number，向可接收 Integer 的父类型容器写入可用 ? super Integer。

② 新题 1｜JVM 的堆内存怎么划分？垃圾回收流程怎样？

原资料：《后端高频面试题大集合》JVM 第 3 题“JVM的堆内存划分和堆内存垃圾回收流程是怎样的”｜PDF 第 38 页。正式后端 #29。

概念

经典分代模型把 Java 堆理解为年轻代和老年代；年轻代传统上再分 Eden、Survivor From、Survivor To。新对象通常优先进入年轻代，经历 GC 后，长期存活对象可能晋升老年代。

Java Heap
├─ Young Generation
│  ├─ Eden
│  ├─ Survivor 0
│  └─ Survivor 1
└─ Old Generation

原理

经典 Serial/Parallel 等分代收集器中，新对象常在 Eden 分配；Young GC 后存活对象在 Survivor 间复制并增加年龄，满足晋升条件后进入老年代。老年代压力大时可能触发老年代回收或 Full GC，具体行为取决于收集器。

为什么

分代思想利用“多数对象朝生夕死”的经验规律：短命对象集中在年轻代可高效批量回收，长期存活对象放入老年代，减少每次扫描成本。

实际项目怎么用

出现频繁 Young GC、晋升过快、老年代持续增长或长暂停时，应结合 GC 日志、对象分配速率、晋升速率、堆占用和业务 RT 一起分析。

AI补充/纠错

纠错：原资料把“Eden 满就 Minor GC、S0/S1 轮转、老年代不足就 Full GC”写成了过于固定的流程。现代 HotSpot 尤其 G1 不宜机械背这条线。G1 把堆切成 Region，年轻代和老年代由不同 Region 动态组成；Young GC、Concurrent Mark、Mixed GC 与 Full GC 的触发也不同。

纠错：对象年龄阈值常见默认 15 是经典 HotSpot 语境中的常见值，不是所有 JVM/GC 的绝对规则，也会受到动态年龄判定等机制影响。

常见坑

  • 把所有 GC 都叫 Full GC。
  • 认为方法结束后对象会立即从堆中消失。
  • 把 Survivor 复制流程当作所有现代收集器的统一实现。
面试口述版：经典分代堆由年轻代和老年代组成，年轻代常分 Eden 与两个 Survivor。大部分对象先在年轻代分配，GC 后存活对象继续留在年轻代或晋升老年代。但现代 G1 使用 Region 管理堆，年轻代区域和大小是动态的，所以我会把 Eden/S0/S1 作为经典分代模型理解，而不会把固定比例和固定触发流程当成所有 JDK 的绝对规则。

③ 新题 2｜JDK 11+ 堆空间比例是不是固定的？

原资料：《后端高频面试题大集合》JVM 第 4 题“新版JDK11以上堆空间里面的划分比例是怎样的？”｜PDF 第 39～40 页。正式后端 #30。

概念

原资料给出经典年轻代 Eden:Survivor:Survivor = 8:1:1、年轻代:老年代约 1:2 的入门比例，并强调具体比例会受到 JVM 配置、应用需求和 GC 策略影响。

原理

经典入门模型：
Young : Old ≈ 1 : 2
Young 内部：Eden : S0 : S1 ≈ 8 : 1 : 1

现代实际：
GC 算法 + 自适应策略 + 参数 + 工作负载
→ 动态决定年轻代及区域分布

固定比例无法同时适应高分配率、低延迟、大堆等不同服务，因此现代收集器越来越依赖自适应调节。

为什么

如果年轻代过小，会导致频繁 Young GC；过大则一次回收要处理更多对象并可能增加暂停。因此合理值依赖对象生命周期与延迟目标。

实际项目怎么用

如果使用 G1，通常先设置总堆和暂停目标，让 G1 自适应；只有在 GC 日志与压测明确证明有问题时才细调，不因为教程写 8:1:1 就在生产强制设置。

AI补充/纠错

重要纠错：题目标题写“JDK11以上”，但答案主体实际上讲的是传统分代比例。JDK 11+ 常用的 G1 中，堆由 Region 组成，Eden/Survivor/Old 是 Region 的动态角色，并不是固定连续三块。现代 Java 25 文档也明确给出 G1 young generation 的最小/最大百分比参数，说明 young size 是可适应变化的，而不是固定 1/3。

常见坑

  • 死背 8:1:1，并声称 JDK 11+ 永远如此。
  • 把 Metaspace 算进 Java Heap。
  • 不了解当前项目到底使用 G1、ZGC 还是其他收集器。
面试口述版：8:1:1 和 1:2 是经典分代模型常见默认认知，不应当作 JDK 11+ 的固定比例。现代 HotSpot 常用 G1，把堆划成 Region，Young/Old 是动态角色，年轻代大小会根据暂停目标和运行情况自适应，因此调优应该看实际收集器和 GC 日志。

G1 Region 是什么？SurvivorRatio、NewRatio 是否还值得手工设置？为什么 G1 一般不建议固定 young generation？

④ 新题 3｜JVM 参数有哪些分类？生产最常看哪些？

原资料：《后端高频面试题大集合》JVM 第 5 题“JVM自带很多参数，列举下有哪些分类和参数案例”｜PDF 第 40～41 页。正式后端 #31。

概念

原资料按 -、-X、-XX 的形式介绍 JVM 参数，并列出 Xms、Xmx、Xmn、Xss、NewRatio、MaxMetaspaceSize、PrintGCDetails 等。

类别例子用途
标准/常规选项-version、-classpathJava 启动器常规行为
-X-Xms、-Xmx、-XssHotSpot 常用扩展配置
-XX-XX:+UseG1GC、-XX:MaxMetaspaceSize=...更细的 JVM/GC 调优项

原理

JVM 参数决定运行时边界和策略，包括堆容量、线程栈、垃圾收集器、元空间、诊断日志等。参数之间可能相互影响，因此性能调优应先从业务指标和日志出发。

为什么

生产问题经常不是“代码 OOM”这么简单，还可能是堆设置不合适、线程数过多导致 native memory 压力、元空间增长、GC 策略不匹配或缺少诊断日志。

实际项目怎么用

java \
  -Xms2g \
  -Xmx2g \
  -Xss1m \
  -XX:+UseG1GC \
  -Xlog:gc*:file=logs/gc.log:time,uptime,level,tags \
  -jar app.jar

排查时先确认“实际生效参数”，再看 GC 日志与运行指标，不要只看启动脚本。容器环境还要结合 cgroup/container memory limit。

AI补充/纠错

版本纠错：原资料示例 -XX:+PrintGCDetails 属于旧式 GC 日志参数；现代 JDK 9+ 更推荐 Unified Logging，例如 -Xlog:gc*。

版本纠错：资料中的 -XX:+UseConcMarkSweepGC 已过时，CMS 在较新的 JDK 中已移除，不应该作为现代生产 JVM 的推荐选项。

纠错：把 -XX 参数统称为“非稳定参数”过于粗糙。面试里更稳妥的说法是：不同参数有不同支持级别，部分诊断/实验参数可能要求 unlock，最终以当前 JDK 的 java 文档和实际 PrintFlagsFinal 为准。

常见坑

  • 只背 Xms/Xmx，不知道项目实际使用什么 GC。
  • 使用旧版 PrintGCDetails 或 CMS 参数回答现代 JDK。
  • 认为 Xms 必须在任何场景都等于 Xmx；这常是服务端稳定性选择，但仍应结合容器与弹性需求。
面试口述版：我会把 JVM 参数分成 Java 启动器常规参数、-X 扩展参数和 -XX 高级参数。生产最常关注堆 Xms/Xmx、线程栈 Xss、GC 选择、元空间和 GC 日志。现代 JDK 我会用 -Xlog:gc* 而不是只背旧版 PrintGCDetails，并以当前 JDK 文档和实际生效参数为准。

可能追问

为什么 Xms/Xmx 常设置一致？Xss 太大会怎样？如何查看 JVM 当前实际参数？

⑤ 新题 4｜你常用哪些大模型相关工具/框架？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.11“你常用哪些大模型相关的工具/框架？”｜PDF 第 9～10 页。原资料按模型调用、Agent 框架、评测、向量数据库、部署运维、编码工具分类。

概念

这题真正考察的是你能不能按“层”组织技术栈，而不是报出几十个产品名。

模型层      → OpenAI / Anthropic / Gemini / 本地模型
应用框架层  → Spring AI / LangChain / LangGraph
RAG 层      → Embedding + VectorStore
Tool 层     → @Tool / MCP / API
评测观测层  → Trace / Evaluation / Metrics
基础设施层  → PostgreSQL / Redis / MQ / Object Storage
工程层      → Docker / CI/CD / Vercel/Cloud/K8s

原理

不同层解决不同问题：模型负责生成与推理，应用框架负责抽象模型和工具，VectorStore 负责语义检索，评测和 Trace 保证可维护性，基础设施负责状态、缓存、异步和持久化。

为什么

面试官更希望听到“为什么选”而不是“我都听过”。如果主技术栈是 Java，回答应围绕 Spring Boot + Spring AI 展开，再说明什么时候会用 Python/LangGraph 等。

实际项目怎么用｜Java/Spring AI 化

Next.js
  ↓
Spring Boot
  ├─ Spring AI ChatClient
  ├─ ChatMemory
  ├─ @Tool / MCP
  ├─ RAG Advisor
  └─ VectorStore
  ↓
PostgreSQL / Redis / MQ / Object Storage
  ↓
外部 LLM API 或私有模型

如果需要模型训练、自托管推理、PyTorch/Transformers 生态，再拆 Python 服务；如果只是调用模型、RAG、Tool Calling，不必为了“AI”强制多一层 FastAPI。

AI补充/纠错

Spring AI 当前补充：Spring AI 2.0.1 已把 Tool Calling Loop 做成 ChatClient Advisor Chain 的一等能力：DefaultChatClient 自动注册 ToolCallingAdvisor，由 ToolCallingManager 执行工具，直到模型不再请求 Tool。工具的真实 API 不直接暴露给模型，应用负责执行，这是重要安全边界。

面试策略：不要声称“每个工具都精通”。按自己真正用过的主线回答：Spring Boot / Spring AI / PostgreSQL(Supabase) / Redis / VectorStore / GitHub / Vercel，再补充了解 LangGraph、LangSmith、Milvus/Qdrant 等即可。

常见坑

  • 工具名堆砌，没有“解决什么问题”。
  • 把 Agent 框架、模型 Provider、向量数据库混在同一层。
  • Python 生态题不做 Java 视角迁移。
面试口述版：我的主栈是 Java，所以应用层主要用 Spring Boot + Spring AI。Spring AI 负责模型调用、RAG、Tool Calling、Memory 和 MCP；数据侧用 PostgreSQL/Supabase，缓存可用 Redis，向量检索按规模选择 pgvector、Milvus 或 Qdrant，文件走对象存储。复杂图状态 Agent 我会了解 LangGraph 的设计思路，但如果 Java 技术栈已经能满足需求，不会为了 AI 强制增加 Python 服务。

可能追问

为什么选择 Spring AI 而不是 LangChain？pgvector 和 Milvus 怎么选？MCP 和普通 Tool Calling 什么关系？

⑥ 新题 5｜Python AI 项目为什么需要虚拟环境？Java 怎么对应？

原资料：《AI大模型面试题-基础篇》第 12 题“在Python环境下开发AI应用时，为什么需要使用虚拟环境？”｜PDF 第 10～11 页。原资料强调依赖隔离、防止全局环境污染、协作与环境复现，并给出 venv/pip/requirements.txt 示例。

概念

Python 虚拟环境的本质是给每个项目建立独立依赖环境，避免项目 A 与项目 B 对同一个包需要不同版本时互相污染。

Project A → venv A → package X 1.x
Project B → venv B → package X 2.x

不共享同一个全局 site-packages
→ 降低版本冲突

原理

python -m venv .venv 创建隔离环境；激活后 pip 安装到该环境。requirements.txt、pyproject.toml/lock 文件用于描述和复现依赖。

为什么

AI 项目依赖经常很多：模型 SDK、numpy、torch、transformers、向量库客户端、Web 框架可能各自约束版本。若全部装在系统 Python，很容易形成“我的电脑能跑，服务器不能跑”。

实际项目怎么用｜Java/Spring 化

Java 不需要照搬 Python venv，因为 Maven/Gradle 天生按项目管理依赖，并从本地仓库解析指定版本：

Spring Boot Project
├─ pom.xml / build.gradle
├─ Maven/Gradle dependency graph
├─ Maven Wrapper / Gradle Wrapper
└─ JDK version

部署再通过 Docker 固化：
JDK + application.jar + env config

更接近 Python venv 的 Java 工程目标是依赖可重复 + JDK 可重复 + 构建工具可重复。可以结合 Maven Wrapper、Toolchains/SDKMAN、容器镜像和 lock/依赖治理实现。

AI补充/纠错

补充：原资料只写 requirements.txt 是入门方案。现代 Python 项目还常用 pyproject.toml，并配合 uv、Poetry、PDM 等管理环境和锁定依赖。

Java 化重点：如果面试官问 Python venv，不要强行答 Maven；先说明原概念，然后补一句“在 Java/Spring 项目中对应的工程目标由 Maven/Gradle + JDK/Wrapper + Docker 来实现”。

常见坑

  • 以为虚拟环境是虚拟机或 Docker。
  • 只创建 venv，却不锁依赖版本。
  • 团队成员使用不同 Python/JDK 和不同构建工具版本，仍然无法复现。
面试口述版：Python 虚拟环境主要用于隔离项目依赖，避免全局包版本冲突，并配合依赖描述文件保证环境复现。Java 不需要完全一样的 venv，因为 Maven/Gradle 已经按项目管理依赖；Java 项目更关注 pom/Gradle 版本、JDK 版本、Wrapper 和 Docker 镜像共同保证构建与运行环境一致。

可能追问

venv 和 Docker 有什么区别？requirements.txt 与 lock file 有什么差异？Maven dependencyManagement 解决什么问题？
