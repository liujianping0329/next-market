① 前一天复习｜先凭记忆回答

复习 1｜线程池生产事故

先回答：为什么“大队列 + 小 corePoolSize”可能让 maximumPoolSize 几乎发挥不了作用？

答完后展开

ThreadPoolExecutor 在达到 corePoolSize 后优先入队，只有队列满才继续扩到 maximumPoolSize。队列过大时，任务可能长期排队，最大线程数迟迟不会触发，最终表现为 queue wait time 与 p99 延迟飙升。

面试口述版：线程池调优不能只看 maximumPoolSize。core 满后任务先入队，因此过大的队列会把压力隐藏成排队延迟，让 max 很难生效；应结合下游容量、队列等待时间、拒绝数和 p99 调整，并做业务线程池隔离。

复习 2｜JVM 是什么

先回答：为什么 Java 能做到“一次编译、多平台运行”？JVM 本身是不是完全跨平台？

答完后展开

Java 源码编译为相对平台中立的字节码，每个平台提供自己的 JVM 实现来执行同一套字节码。JVM 实现本身仍然依赖具体 OS/CPU。

复习 3｜JVM 运行时数据区域

先回答：程序计数器、虚拟机栈、本地方法栈、堆、方法区中，哪些主要是线程私有，哪些共享？

答完后展开

程序计数器、虚拟机栈、本地方法栈主要线程私有；堆和方法区是 JVM 线程共享区域。方法区是规范概念，HotSpot JDK 8+ 的类元数据主要放在 Metaspace。

复习 4｜Agent 技术趋势

先回答：近一年 Agent 工程化最值得关注的三个方向是什么？

答完后展开

可概括为：编码 Agent 从补全走向长任务执行；MCP/Agent Framework 等互操作和编排能力成熟；企业部署更重视权限、Trace、Evaluation 与治理，而不只看模型效果。

复习 5｜LangChain 生态

先回答：LangChain、LangGraph、LangSmith 各自更偏哪一层？Java 项目如何映射？

答完后展开

LangChain 偏 LLM 应用抽象，LangGraph 偏有状态 Agent Workflow，LangSmith 偏 Trace/Evaluation。Java 侧可用 Spring AI 承担 Model/RAG/Tool/Memory/MCP，再由 Spring Service/Workflow 管理复杂状态。

间隔复习｜约 3 天前：ThreadLocal

ThreadLocalMap 的 Key 是弱引用，为什么 Value 仍可能滞留？

答完后展开

GC 可以让 Entry 的 key 变 null，但 value 仍被 Entry 强引用；若线程池线程长期存活且没有 remove，stale entry 可能持续存在并导致上下文污染。

间隔复习｜约 7 天前：Java 泛型

为什么 List<String> 不是 List<Object> 的子类型？PECS 又解决什么问题？

答完后展开

Java 泛型默认是不变的。PECS 用通配符表达读写边界：Producer Extends，Consumer Super；读取 Number 子类型集合用 ? extends Number，写入 Integer 到其父类型容器用 ? super Integer。

② 新题 1｜JVM 的堆内存怎么划分？垃圾回收流程怎样？

原资料：《后端高频面试题大集合》JVM 第 3 题“JVM的堆内存划分和堆内存垃圾回收流程是怎样的”｜PDF 第 38 页。正式后端 #29。

概念

经典分代模型把 Java 堆理解为年轻代和老年代；年轻代传统上再分 Eden、Survivor From、Survivor To。新对象通常优先进入年轻代，经历多次 GC 后，长期存活对象可能晋升老年代。

Java Heap
├─ Young Generation
│  ├─ Eden
│  ├─ Survivor 0
│  └─ Survivor 1
└─ Old Generation

原理

经典 Serial/Parallel 等分代收集器中，新对象常在 Eden 分配；年轻代空间不足时触发 Young GC，存活对象在 Survivor 区之间复制并增加年龄，满足晋升条件后进入老年代。老年代空间压力大时可能触发老年代回收或 Full GC，具体行为取决于 GC 实现。

为什么

分代思想来自“绝大多数对象朝生夕死”的经验规律。把生命周期短的对象集中处理，可以用复制等低成本算法快速回收大量垃圾，而老年代采用更适合高存活率对象的策略。

实际项目怎么用

出现频繁 Young GC、晋升过快、老年代增长或长时间暂停时，应结合 GC 日志、对象分配速率、晋升速率、堆占用和业务 RT 一起分析，而不是只凭一次 Full GC 判断。

AI补充/纠错

纠错：原资料把“Eden 满就 Minor GC、S0 满就 Minor GC、老年代不足就 Full GC”描述得过于固定。现代 HotSpot，尤其 G1，不应该机械按这条流程背。G1 把堆切成 Region，并动态组合年轻代/老年代区域；触发条件也由收集器策略、分配压力和 IHOP 等因素决定。

纠错：对象年龄阈值“默认 15”是经典 HotSpot 语境中的常见值，但不是跨 JVM/GC 的绝对规则，也可能受动态年龄判定等机制影响。

常见坑

  • 把所有 GC 都叫 Full GC。
  • 认为方法结束后对象立刻从堆消失。
  • 把 Survivor 复制流程当成所有现代 GC 的统一实现。
面试口述版：经典分代堆由年轻代和老年代组成，年轻代常分 Eden 与两个 Survivor。大多数新对象先在年轻代分配，Young GC 后存活对象继续复制或晋升，长期存活对象进入老年代。但现代 G1 以 Region 管理堆，年轻代大小和区域分配是动态的，所以我会把“Eden/S0/S1”作为经典分代模型理解，不把固定比例和固定触发流程当成所有 JDK 的绝对规则。

③ 新题 2｜JDK 11+ 堆空间比例是不是固定的？

原资料：《后端高频面试题大集合》JVM 第 4 题“新版JDK11以上堆空间里面的划分比例是怎样的？”｜PDF 第 39～40 页。正式后端 #30。

概念

原资料给出经典年轻代 Eden:Survivor:Survivor = 8:1:1、年轻代:老年代约 1:2 的入门比例，并指出元空间使用本地内存。

原理

这些比例主要帮助理解传统分代堆，但 JVM 实际布局受 GC 收集器、参数、自适应策略、堆大小和业务对象生命周期共同影响。

经典入门模型：
Young : Old ≈ 1 : 2
Young 内部：Eden : S0 : S1 ≈ 8 : 1 : 1

现代实际：
GC 算法 + 自适应策略 + 参数 + 工作负载
→ 动态决定年轻代及 Region 分布

为什么

固定比例很难同时适配高对象分配率、低延迟服务、大堆服务等不同场景，所以现代收集器越来越依赖自适应调节而不是要求开发者死设代比例。

实际项目怎么用

如果使用 G1，通常先设置总堆和暂停目标，让 G1 自适应；只有在有明确 GC 数据与压测证据时才考虑更细粒度参数。不要因为“教程写 8:1:1”就在生产强行设置。

AI补充/纠错

重要纠错：题目标题写“JDK11以上”，但正文又写“在JDK8中，堆空间划分比例如下”，本身就存在版本表述不一致。更关键的是，从 JDK 9 起 G1 成为 HotSpot 默认 GC；G1 的年轻代由 Region 动态组成，因此不存在一个必须背诵的“JDK11+ 固定 8:1:1”规则。

补充：Metaspace 不属于 Java Heap，使用本地内存；它与年轻代/老年代比例不是同一维度。

常见坑

  • 把 8:1:1 当成 JDK 11/17/21 的固定物理布局。
  • 把 Metaspace 当成 Old Generation 的一部分。
  • 未确认 GC 类型就直接套 NewRatio/Xmn 调优。
面试口述版：8:1:1 和 Young:Old 约 1:2 是传统分代堆的经典默认认知，但不能说 JDK11+ 一定固定这样。现代 HotSpot 默认 G1，堆由 Region 管理，年轻代大小会动态调整。实际调优先确认收集器和 GC 日志，再决定是否需要干预年轻代比例。

可能追问

为什么 G1 不建议固定 -Xmn？Region 是什么？Metaspace 在哪里？

④ 新题 3｜JVM 参数有哪些分类？现代 JDK 怎么写？

原资料：《后端高频面试题大集合》JVM 第 5 题“JVM自带很多参数，列举下有哪些分类和参数案例”｜PDF 第 40～41 页。正式后端 #31。

概念

类型示例用途
标准/常用选项-version、-classpathJava 启动与基础行为
-X-Xms、-Xmx、-Xss堆、栈等常见运行参数
-XX-XX:MaxMetaspaceSize=...HotSpot 高级参数
Unified Logging-Xlog:gc*现代 JDK GC/VM 日志

原理

常见内存参数：

-Xms2g                 # 初始堆
-Xmx2g                 # 最大堆
-Xss1m                 # 每线程栈
-XX:MaxMetaspaceSize=512m
-Xlog:gc*               # 现代 GC 日志

为什么

JVM 参数不是“越多越专业”。参数越多，越可能覆盖 GC 的自适应策略。生产上应围绕明确目标配置：内存边界、GC 目标、OOM 诊断、日志与容器资源。

实际项目怎么用

java \
  -Xms2g -Xmx2g \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/logs/heap.hprof \
  -Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags \
  -jar app.jar

AI补充/纠错

重要纠错：原资料把 -XX:+PrintGCDetails 当成常用示例，但 JDK 9 引入 Unified JVM Logging 后，-XX:+PrintGCDetails 与 -XX:+PrintGC 已被废弃，现代 JDK 应优先使用 -Xlog:gc / -Xlog:gc*。

重要纠错：原资料列出的 -XX:+UseConcMarkSweepGC 属于旧 CMS 收集器参数；CMS 已从现代 JDK 移除，今天面试不应把它当当前推荐配置。

补充：-Xms = -Xmx 是一些服务端部署的常见稳定性做法，但不是所有应用都必须如此，容器环境还要结合 MaxRAMPercentage 等资源策略。

常见坑

  • 背一堆参数却不知道使用哪个 GC。
  • 仍用 PrintGCDetails 作为 Java 17/21 的主推荐日志参数。
  • 把旧 CMS 参数用于现代 JDK。
  • 只设置 -Xmx，不考虑非堆、线程栈、Direct Memory 和容器总内存。
面试口述版：JVM 参数常见包括 -Xms/-Xmx/-Xss 这类运行参数和 -XX 高级 HotSpot 参数。现代 JDK 的 GC 日志应优先用 Unified Logging，例如 -Xlog:gc*，而不是继续把 PrintGCDetails 当主方案。生产配置要同时考虑堆、元空间、线程栈、Direct Memory 和容器内存，并以监控和压测为依据。

可能追问

-Xms 和 -Xmx 为什么经常设成一样？OOM 后怎么自动 dump？容器里怎样限制 JVM 内存？

⑤ 新题 4｜你常用哪些大模型相关工具 / 框架？

概念

这题不是让你报菜名，而是考察你能否按工程层次讲出完整 AI 应用工具链。

层次原资料示例Java/Spring AI 视角

为什么

面试官真正想确认的是：你有没有把模型接入、RAG、Tool、Memory、评测、部署这些能力组合成一个工程系统的经验，而不是只会调用一次 Chat API。

Next.js

Spring Boot + Spring AI
├─ ChatClient
├─ @Tool / ToolCallback
├─ ChatMemory

AI补充/纠错

Java 化：当前 Spring AI 稳定版为 2.0.1，官方 API 已覆盖 Model API、Vector Store、Tool Calling、ChatClient、Advisors、MCP、ETL 与 Observability。对 Java 后端候选人来说，与其照抄 Python 技术栈，不如明确说“应用主干用 Spring Boot + Spring AI；需要 PyTorch/Transformers/自托管推理时再拆 Python 服务”。

补充：大型 Tool/MCP 集合还要关注 tool context bloat、权限过滤和工具命名冲突，不应把所有工具无条件暴露给每次模型请求。

常见坑

  • 只报框架名，不说自己在哪一层使用。
  • Java 项目为了“AI”强行再加 FastAPI，形成无意义跳转。
  • 把 VectorStore 当数据库权限系统，忽略 ACL。
  • 没有 Evaluation/Trace，就无法判断 Prompt 或模型升级是否回归。
面试口述版：我会按模型、RAG/Agent、评测观测、存储和部署分层回答。我的主技术栈是 Spring Boot + Spring AI，模型调用用 ChatClient，RAG 用 VectorStore + Advisor，工具用 @Tool/MCP，Memory 用 ChatMemory，并结合 Spring Observability 做 Trace。需要模型训练、自研推理或复杂 Python AI 生态时，再拆 FastAPI/Python 服务。

⑥ 新题 5｜Python AI 开发为什么需要虚拟环境？Java 怎么对应？

原资料：《AI大模型面试题-基础篇》第 12 题“在Python环境下开发AI应用时，为什么需要使用虚拟环境？”｜PDF 第 10～11 页。

概念

Python 虚拟环境的核心是给每个项目提供独立依赖空间，避免全局 Python 环境被不同项目的包版本互相污染。

Project A → venv A → package X 1.x
Project B → venv B → package X 2.x

互不冲突

原理

python -m venv 会创建项目隔离的 Python 解释器/路径环境；激活后 pip 安装的包进入该环境，而不是全局 site-packages。依赖通常再通过 requirements.txt、Poetry、uv 等方式锁定和复现。

为什么

AI/Python 项目依赖非常复杂，Torch、Transformers、CUDA 相关包、LangChain 生态等版本变化快。没有环境隔离，很容易出现“我的机器能跑、换一台就坏”的问题。

实际项目怎么用

python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 退出
deactivate

AI补充/纠错｜Java / Spring Boot 对应理解

Java 化：Java 通常不需要像 Python 那样每个项目创建 venv，因为 Maven/Gradle 本身会按项目声明依赖，并从本地仓库解析版本；构建输出的 classpath 是项目级的。类似的“可复现环境”主要靠：

pom.xml / build.gradle 固定依赖 → Maven/Gradle Wrapper 固定构建工具 → Toolchains/容器固定 JDK → Docker 固定运行环境。

因此面试可以回答：Python 用 venv 隔离解释器和 site-packages；Java 主要靠 Maven/Gradle 的项目级依赖图、Wrapper、JDK Toolchain 和容器实现类似目标。

常见坑

  • 把 venv 说成 Docker。venv 主要隔离 Python 依赖，不隔离 OS、网络、CPU、系统库。
  • 只创建 venv，不锁依赖版本，仍然无法稳定复现。
  • Java 项目只写 pom.xml，却没有固定 JDK 与 Maven/Gradle 版本。
面试口述版：Python 虚拟环境主要解决项目依赖隔离与环境复现，避免不同项目的包版本污染全局环境。Java 中类似问题通常由 Maven/Gradle 的项目级依赖、Wrapper、JDK Toolchain 和 Docker 解决，因此 Spring AI 项目不需要额外模仿 Python 建 venv，但仍要固定依赖和运行时版本。
