复习 1｜线上死锁排查

先回答：接口卡死后如何排查 Java 死锁？为什么不能看到 BLOCKED 就直接判死锁？

答完后展开

连续抓多份 thread dump，分析谁持锁、谁等待，确认是否形成循环等待；BLOCKED 也可能只是普通竞争。

口述版：我会先用 jstack/jcmd 保留多份线程快照，分析锁持有与等待关系，确认循环等待，再回代码检查嵌套锁和顺序，通常通过统一加锁顺序、缩小临界区或 tryLock 超时解决。

复习 2｜ThreadLocal

先回答：ThreadLocal 是加锁吗？为什么适合保存 userId/traceId/tenantId？

答完后展开

不是加锁，而是利用每个 Thread 自己的 ThreadLocalMap 做线程内上下文隔离。

复习 3｜Thread / ThreadLocal / ThreadLocalMap

先回答：值存在哪里？一个线程是不是只能存一个 ThreadLocal 值？

答完后展开

值在当前 Thread 的 ThreadLocalMap 中；一个 ThreadLocalMap 可有多个 ThreadLocal→Value 条目，所以一个线程当然可以保存多个不同 ThreadLocal 值。

间隔复习｜约 3 天前：动态代理

先回答：JDK 动态代理与类代理区别？为什么 Spring AOP 自调用可能失效？

答完后展开

JDK 动态代理基于接口，类代理通过生成子类增强；同类内部直接 self-invocation 可能绕过代理对象，因此事务等切面不生效。

② 新题 1｜JVM 四大引用是什么？

原资料：《后端高频面试题大集合》JUC 第 7 题“JVM里面的四大引用是哪些？使用场景有哪些”｜PDF 第 24～28 页。正式后端 #20。

概念

引用GC 语义典型用途
强引用强可达时普通 GC 不回收普通对象
软引用内存压力下可回收内存敏感对象
弱引用只剩弱引用时 GC 可回收ThreadLocalMap Key 等
虚引用不能用 get 获得对象，配合 ReferenceQueue回收跟踪/清理机制

原理

强 → 最强生命周期约束
软 → 内存压力时让步
弱 → GC 时可让步
虚 → 不负责保活，主要感知回收阶段

为什么

不同引用强度让 JVM 能在普通对象、缓存、元数据关联、回收跟踪之间采用不同生命周期策略。

项目怎么用

ThreadLocalMap.Entry
 key = WeakReference<ThreadLocal<?>>
 value = 普通强引用对象

AI补充/纠错

纠错：原资料使用 finalize() 演示 GC。现代 Java 不应把 finalization 当推荐资源清理方案。Object.finalize 已 deprecated for removal；优先 AutoCloseable + try-with-resources，特定场景用 Cleaner 或 PhantomReference + ReferenceQueue。软引用也不应替代有明确容量/过期/淘汰策略的生产缓存。

常见坑

  • 把弱引用理解成对象会立刻回收。
  • 认为 PhantomReference.get() 能拿到对象。
  • 依赖 System.gc() 保证立即回收。
面试口述版：Java 有强、软、弱、虚四种引用。强引用是普通对象引用；软引用在内存压力下可回收；弱引用只剩弱关联时 GC 即可回收；虚引用主要配合 ReferenceQueue 跟踪对象回收。ThreadLocalMap 的 Key 就使用弱引用。现代 Java 不推荐 finalize 做资源清理。

WeakHashMap、ReferenceQueue、Cleaner、finalize 为什么被弃用？

③ 新题 2｜ThreadLocal 为什么 Key 是弱引用？为什么还必须 remove？

原资料：《后端高频面试题大集合》JUC 第 8 题“ThreadLocal为啥需要设计成弱引用，用完需要remove呢?”｜PDF 第 28～30 页。正式后端 #21。

概念与原理

Thread
└── ThreadLocalMap
    └── Entry
        ├── key   = WeakReference<ThreadLocal>
        └── value = 普通强引用

Key 用弱引用是为了业务侧不再持有 ThreadLocal 后，ThreadLocal 本体不会仅因 Map 的 Key 而永久存活。但 Key 被 GC 后可能留下 key=null、value 仍强引用的 stale entry。

为什么要 remove

Entry
key = null
value = UserContext / 大对象  ← 仍可能被线程长期持有

线程池线程长期存活时，value 可能长期滞留；线程复用还可能造成上下文串数据。

项目怎么用

try {
    UserContextHolder.set(ctx);
    service.handle();
} finally {
    UserContextHolder.remove();
}

AI补充/纠错

ThreadLocalMap 的部分 set/get/remove 路径会顺手清理 stale entry，但不能据此省略 remove。普通 ThreadLocal 也不会自动跨新线程/线程池任务传播上下文。

常见坑

  • 只记“Key 是弱引用，所以不会泄漏”。
  • 忽略线程池线程长期存活。
  • 忘记 finally 清理导致 userId/tenantId 串请求。
面试口述版：ThreadLocalMap 的 Entry 对 ThreadLocal Key 使用弱引用，让外部强引用消失后 Key 可被 GC；但 value 仍是强引用，线程池线程长期存活时可能产生 stale entry。使用完必须在 finally 中 remove，既减少内存滞留，也避免线程复用导致上下文污染。

可能追问

ThreadLocalMap 为什么不用 HashMap？如何处理冲突？InheritableThreadLocal 有什么问题？

④ 新题 3｜CompletableFuture 有什么用途？

原资料：《后端高频面试题大集合》JUC 第 9 题“说下CompletableFuture的用途和使用场景”｜PDF 第 30～31 页。正式后端 #22。

概念

CompletableFuture 同时实现 Future 和 CompletionStage，不只代表未来结果，还能组合、转换、并行聚合和异常处理。

原理

串行：A(200ms) → B(300ms) → C(400ms) ≈ 900ms
并行：A ─┐
      B ─┼→ allOf/thenCombine → 汇总
      C ─┘
总时间更接近最慢任务 + 汇总开销

项目怎么用

var profile = CompletableFuture.supplyAsync(
    () -> profileService.load(userId), bizExecutor);
var orders = CompletableFuture.supplyAsync(
    () -> orderService.queryRecent(userId), bizExecutor);
var result = profile.thenCombine(orders, DashboardDto::new).join();

AI补充/纠错

纠错：默认 Async 方法通常使用 ForkJoinPool.commonPool()，但不能简单永久背成“线程数=CPU核心数”。生产慢 I/O 不应全部挤 commonPool，应按业务使用独立 Executor。无 Async 的 continuation 执行线程也不应绝对化理解。

常见坑

  • 并行过度压垮下游。
  • 不处理异常。
  • 业务共用 commonPool 导致线程饥饿。
  • 最后无脑 join 又把请求线程阻塞。
面试口述版：CompletableFuture 是 Java 8 的异步任务编排工具，适合多个独立数据源并行查询、任务依赖组合、流水线转换和异常兜底。生产中我会为慢 I/O 使用隔离线程池，并用 thenCombine、allOf、exceptionally 等 API 管理组合与失败。

可能追问

thenApply vs thenCompose？allOf 如何取结果？join vs get？线程池如何配置？

⑤ 新题 4｜Agent Loop 是什么？如何防止死循环？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.8“Agent Loop 听说过吗？”｜PDF 第 7 页。

概念

while not done:
  Perceive  感知
  Think     思考
  Act       行动
  Observe   观察
  Evaluate  判断是否完成

原理与为什么

真实任务往往需要查库、读文件、调用工具、观察结果再判断。Loop 让 Agent 获得多步执行能力。

Spring AI / Java 化

ChatClient
  ↓
ToolCallingAdvisor
  ↓
ChatModel
  ↓
Tool Call?
  ├─ Yes → ToolCallingManager → Tool Result → 再进模型
  └─ No  → Final Response

AI补充/纠错

版本纠错：不要把 context.addObservation() 当 Spring AI API；那只是概念伪代码。Spring AI 2.0 的正式关键组件是 ToolCallingAdvisor 与 ToolCallingManager。标准 Tool Loop 也不等于完整 Agent Orchestration，复杂 Planning、长期状态、审批、补偿和 Workflow 仍可能由 Java Service 层控制。

防死循环

策略作用
max iterations限制最大循环次数
timeout限制总执行时间
重复 Tool 检测识别没有进展的循环
Token/成本预算限制费用
错误恢复重试、换工具、降级、退出
面试口述版：Agent Loop 是感知、思考、行动、观察、评估的循环。Spring AI 2.0 对标准 Tool Calling Loop 已有 ToolCallingAdvisor 和 ToolCallingManager 支持，但生产 Agent 还需要最大迭代、超时、重复调用检测、成本预算、状态管理和错误恢复。

Tool Calling Loop 与 ReAct 区别？如何自定义 Advisor？Agent 状态放哪里？

⑥ 新题 5｜AI 项目为什么需要架构图？

原资料：《AI大模型面试题-基础篇》第 8 题“在AI项目中，为什么需要绘制架构图？不同类型架构图的作用是什么？”｜PDF 第 7～8 页。

概念

架构图的价值不是画得漂亮，而是降低复杂系统沟通成本，让不同角色看到自己关心的信息。

原资料内容

类型重点
产品/应用架构业务能力、模块边界
技术架构技术选型、组件关系

AI补充/纠错

企业 AI 项目建议再补数据/RAG、部署、安全权限三个视角：

文件 → 解析 → Chunk → Embedding → VectorStore → 检索 → LLM
用户 → Spring Boot → Auth/ACL → Spring AI → DB/Redis/MQ/Object Storage
安全 → Prompt Injection / Tool 权限 / 敏感数据 / Audit

实际项目怎么用

Web
 ↓
Spring Boot
 ├─ Auth / ACL
 ├─ File Service
 ├─ RAG Service
 └─ Spring AI ChatClient
      ├─ RAG Advisor
      └─ @Tool
 ↓
DB / Redis / MQ / Object Storage / VectorStore
 ↓
LLM Provider / 私有模型

常见坑

  • 一张图塞所有信息。
  • 只堆技术 Logo，没有数据流/调用方向。
  • AI 图只画“用户→LLM”，没有 RAG、ACL、Fallback、Observability。
面试口述版：架构图用于降低复杂系统沟通成本。产品架构图强调业务能力和模块边界，技术架构图说明技术组件及关系；AI 项目我还会补数据/RAG、部署和安全权限视角，把文档如何进入向量库、检索如何做 ACL、模型如何调用 Tool、服务如何部署和监控表达清楚。
