复习 1｜JVM 四大引用

先回答：强、软、弱、虚引用的 GC 语义分别是什么？哪一种与 ThreadLocalMap 的 Key 直接相关？

答完后展开

强引用维持普通强可达；软引用可在内存压力下回收；弱引用只剩弱关联时可被 GC；虚引用不用于取得对象，通常配合 ReferenceQueue 感知回收。ThreadLocalMap.Entry 的 Key 使用 WeakReference。

面试口述版：Java 有强、软、弱、虚四种引用。强引用是普通引用；软引用在内存压力下可回收；弱引用只剩弱关联时 GC 即可回收；虚引用主要用于配合 ReferenceQueue 跟踪回收过程。ThreadLocalMap 的 Key 使用弱引用。

复习 2｜ThreadLocal 为什么还要 remove？

先回答：Key 已经是弱引用，为什么在线程池里仍然必须 finally + remove()？

答完后展开

Key 被 GC 后可能形成 key=null，但 value 仍由 ThreadLocalMap 强引用。线程池线程长期存活时，value 可能长期滞留；线程复用还可能造成 userId/tenantId 等上下文污染。

面试口述版：弱引用只能帮助 ThreadLocal Key 被回收，不能自动释放 Entry 的 Value。在线程池中线程长期复用，因此必须在 finally 中 remove，降低 stale entry 滞留和上下文串请求风险。

复习 3｜CompletableFuture

先回答：它比普通 Future 多解决了什么问题？为什么生产慢 I/O 一般不建议全部共用 commonPool？

答完后展开

CompletableFuture 支持任务转换、串联、并行聚合、异常处理。大量慢 I/O 共用 commonPool 会占住共享工作线程，影响其他异步任务，生产环境通常使用业务隔离 Executor。

复习 4｜Agent Loop

先回答：Agent Loop 的 Perceive → Think → Act → Observe → Evaluate 分别在做什么？怎样防止死循环？

答完后展开

通过 maxIterations、timeout、重复工具调用检测、Token/Cost Budget、失败重试与“无进展退出”等机制限制循环。Spring AI 的标准 Tool Calling Loop 可由 ToolCallingAdvisor 驱动，但生产级状态与审批仍需额外编排。

复习 5｜AI 架构图

先回答：产品/应用架构图与技术架构图有什么不同？AI 项目还值得补哪几种视角？

答完后展开

产品架构强调业务能力和模块边界，技术架构强调组件、技术选型和调用关系。AI 项目还适合补 RAG 数据流、部署架构、安全/ACL 与可观测性视角。

间隔复习｜约 3 天前：ReentrantLock

默认公平还是非公平？“非公平”是否等于随机？

答完后展开

默认非公平；它允许新线程先尝试 barging 抢锁，不等于随机。抢不到后仍进入 AQS 等待队列。

间隔复习｜约 7 天前：hashCode / equals

为什么 hashCode 相同不代表 equals 相同？

答完后展开

哈希可能冲突；hashCode 用于缩小查找范围，equals 用于最终确认。equals 为 true 时 hashCode 必须相同，但反过来不成立。

② 新题 1｜什么是池化思想？有哪些应用场景？

原资料：《后端高频面试题大集合》JUC 第 10 题“说下什么是池化思想，有哪些应用场景”｜PDF 第 31 页。正式后端 #23。

概念

池化就是：提前创建并维护一组昂贵资源，需要时借用，使用后归还并复用，减少每次创建/销毁的成本，同时控制资源总量。

原理

没有池化：请求 → 创建资源 → 使用 → 销毁
池化：请求 → Pool → 借出资源 → 使用 → 归还

池本质上同时做两件事：①复用昂贵对象；②给资源数量设置边界，避免无限创建。

为什么

线程、数据库连接、网络连接等创建和销毁都不是零成本。高并发下频繁创建不仅慢，还可能造成线程数、连接数或内存失控。池化通过“复用 + 限流”换取稳定吞吐。

实际项目怎么用

线程池：ThreadPoolExecutor
数据库连接池：HikariCP
HTTP连接池：HTTP Client Connection Pool
对象池：少数初始化成本极高且可安全复用的资源

例如 Spring Boot 访问数据库时，通常不是每次 SQL 都新建数据库连接，而是从 HikariCP 借一个连接，事务结束后归还池中。

AI补充/纠错

纠错：不是“所有对象都适合对象池”。现代 JVM 创建普通短命小对象很便宜，强行池化普通 DTO 反而会增加生命周期、同步和脏状态管理复杂度。池化最适合创建昂贵、数量必须受控、可以安全复用的资源。

常见坑

  • 只记“提高性能”，忘了池化还承担资源上限与背压。
  • 池越大越好——错误，池过大会增加上下文切换、连接竞争和下游压力。
  • 对象归还前没有重置状态，造成请求之间数据污染。
面试口述版：池化思想就是提前创建并维护一组昂贵资源，使用时从池里获取，使用后归还复用。它既减少创建销毁成本，也控制资源总量。常见例子有线程池、数据库连接池、HTTP 连接池。实际参数不能越大越好，需要根据下游容量、任务类型和压测结果配置。

可能追问

为什么数据库连接池不能无限大？连接池耗尽怎么排查？对象池为什么现在没有以前常见？

③ 新题 2｜ThreadPoolExecutor 的设计原理和核心参数

原资料：《后端高频面试题大集合》JUC 第 11 题“说下ThreadPoolExecutor设计原理和核心参数”｜PDF 第 32～33 页。正式后端 #24。

概念

ThreadPoolExecutor 是 Java Executor 框架的核心线程池实现。面试重点不是背 7 个构造参数，而是讲清任务进入线程池后的决策顺序。

原理｜任务提交流程

execute(task)
   ↓
worker < corePoolSize ?
   ├─ Yes → 创建线程执行
   └─ No → workQueue 能入队？
             ├─ Yes → 排队
             └─ No → worker < maximumPoolSize ?
                       ├─ Yes → 扩容线程执行
                       └─ No → 拒绝策略
参数作用
corePoolSize核心线程数
maximumPoolSize线程总数上限
keepAliveTime + unit超过 core 的空闲线程最大存活时间
workQueue缓存待执行任务
threadFactory创建线程、设置名称等
handler线程和队列都满时的拒绝策略

为什么

这个设计允许在“线程数量”和“排队长度”之间做取舍：队列太大，延迟和内存风险上升；线程太多，CPU 上下文切换和下游压力上升。

实际项目怎么用

ExecutorService executor = new ThreadPoolExecutor(
    16, 64, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.CallerRunsPolicy()
);

在 Spring Boot 项目里，可以把外部 AI API、数据库分析、文件解析等慢任务使用不同 Executor 隔离，避免一个模块拥塞拖垮其他模块。

AI补充/纠错

纠错 1：原资料写“核心线程即使没有任务也会一直存活”作为默认理解可以，但 Java 允许通过 allowCoreThreadTimeOut(true) 让核心线程也超时退出。
纠错 2：线程池大小不存在“CPU 核心数/2倍核心数”这样的万能公式。CPU 密集、I/O 密集只能作为初始估算，最终要结合阻塞比例、下游限流、RT、队列等待、CPU、内存和压测结果。

常见坑

  • 队列使用无界或超大容量，maximumPoolSize 长期几乎不起作用。
  • DiscardPolicy 静默丢任务却没有监控。
  • 多个不同业务共用一个池，出现线程饥饿。
  • 只看线程数量，不监控 queue size、active count、reject count。
面试口述版：ThreadPoolExecutor 收到任务后，先看核心线程是否够，不够就创建；核心线程满后优先入队；队列也满了才继续扩容到 maximumPoolSize；线程和队列都满则触发拒绝策略。生产调优重点是任务特征、队列长度、下游容量和压测，而不是死背 CPU 核心数公式。

可能追问

四种拒绝策略？为什么无界队列会让 maximumPoolSize 失效？CallerRunsPolicy 的背压效果是什么？

④ 新题 3｜Executors 自带哪些线程池？生产怎么选？

原资料：《后端高频面试题大集合》JUC 第 12 题“说下java自带的Executors线程池种类和特点”｜PDF 第 33～34 页。正式后端 #25。

概念

工厂方法核心特点
newFixedThreadPool(n)固定数量 worker；共享无界队列
newSingleThreadExecutor()单 worker 串行；无界队列
newCachedThreadPool()按需创建/复用线程；SynchronousQueue；线程数可能快速增长
newScheduledThreadPool(n)延迟、周期调度任务

原理与为什么

这些方法本质上是把 ThreadPoolExecutor / ScheduledThreadPoolExecutor 的一组参数包装成快捷配置，适合简单场景，但隐藏参数也意味着你可能忽略队列和线程数量上限。

实际项目怎么用

对于需要明确 SLA 和限流的 Web/Spring 服务，更常见的做法是显式配置 ThreadPoolExecutor 或 Spring 的 ThreadPoolTaskExecutor，把核心线程、最大线程、队列容量、线程名、拒绝策略和监控指标都写清楚。

AI补充/纠错

现代 Java 视角：Oracle Java 21 文档明确说明 newFixedThreadPool 和 newSingleThreadExecutor 使用共享无界队列；newCachedThreadPool 会按需创建线程。生产高负载服务若直接使用这些默认配置，可能出现队列无限增长或线程数膨胀。Java 21 还提供 newVirtualThreadPerTaskExecutor()，它为每个任务创建虚拟线程，但虚拟线程不会增加数据库连接、外部 API QPS 等下游容量，仍然需要连接池、Semaphore 或限流。
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f = executor.submit(() -> remoteApi.call());
}

常见坑

  • 认为 FixedThreadPool 的队列是有界的。
  • 认为 CachedThreadPool 会自动限制最大线程数。
  • ScheduledThreadPool 任务异常或 shutdown 没处理。
  • 把虚拟线程当成“所有限流都不用了”。
面试口述版：Executors 提供 Fixed、Cached、Single、Scheduled 等常用线程池快捷工厂。Fixed 和 Single 使用无界队列，Cached 可以快速扩张线程，所以生产高流量服务要特别注意资源上限。我更倾向显式配置 ThreadPoolExecutor 或 Spring ThreadPoolTaskExecutor；Java 21 的 I/O 场景也可以考虑虚拟线程，但下游连接数和 QPS 仍要独立限流。

可能追问

FixedThreadPool 为什么可能 OOM？SynchronousQueue 是什么？平台线程和虚拟线程怎么选？

⑤ 新题 4｜当前 Agent 技术难以突破的核心瓶颈有哪些？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.9“你认为当前 Agent 技术难以突破的核心瓶颈有哪些？”｜PDF 第 7～8 页。

概念

原资料把 Agent 投产难点分成七类：可靠性、规划能力、成本与延迟、长上下文退化、安全与可控性、评测标准、可观测性。

瓶颈本质工程对策
Reliability一步错后续级联；幻觉会变成错误动作结构化输出、Tool 参数校验、重试/补偿
Planning长任务计划容易偏离目标显式 Plan、checkpoint、状态机、重规划
Cost / Latency多一步就可能多一次模型/工具调用模型路由、缓存、并行工具、预算与 maxIterations
Context Rot上下文越长不代表利用越稳定滑动窗口、摘要、RAG、结构化状态
SafetyAgent 能执行真实副作用最小权限、Tool 白名单、Human Approval、审计
Evaluation动态多步任务难用单一准确率衡量任务成功率、Tool 选择正确率、回归评测集
Observability难判断错在 LLM、Tool、Context 还是 WorkflowTrace、step spans、tool/result、成本与延迟监控

为什么

普通聊天模型“答错一句”通常只是文本错误；Agent 的错误可能转化为真实副作用，例如写错数据库、发送错误邮件或反复调用昂贵 API，因此可靠性和可控性要求明显更高。

实际项目怎么用｜Spring AI / Java 化

Controller
  ↓
AgentService
  ├─ state / maxIterations / timeout
  ├─ ChatClient
  ├─ @Tool whitelist
  ├─ RAG / ACL
  ├─ retry / fallback
  ├─ approval gate
  └─ observability / audit

例如“自然语言 → SQL”项目，不应该让模型直接拥有无限制数据库能力；可以让模型输出结构化查询意图，再由 Java 校验表/字段白名单和 SELECT-only 规则，最后执行只读 SQL。

AI补充/纠错

原资料中的若干百分比和行业调研数字属于阶段性数据，面试不建议把具体比例作为核心答案。更稳的方式是讲清七类瓶颈及工程对策。Agent 越自主，通常越需要把确定性约束放回 Java/Workflow 层。

常见坑

  • 把“模型更强”当成可靠性的唯一解法。
  • 只做成功 Demo，不设计失败路径。
  • 日志只记录最终回答，不记录 Tool Call 和步骤状态。
  • 高风险 Tool 没有最小权限或人工确认。
面试口述版：我认为 Agent 当前最大的瓶颈不是单一模型能力，而是可靠性、规划、成本延迟、长上下文退化、安全、评测和可观测性。因为 Agent 会执行真实动作，一步推理错误可能级联成错误 Tool Call。生产中要用结构化状态、maxIterations、Tool 白名单、权限与审批、回归评测、Trace 和 Java 侧确定性校验，把自主性限制在可控范围内。

⑥ 新题 5｜LangChain 的核心功能解决什么问题？Spring AI 怎么对应？

原资料：《AI大模型面试题-基础篇》原资料第 10 题“说下LangChain框架的核心功能，解决大模型开发中的哪些问题?”｜PDF 第 8～9 页。题号说明：该 PDF 在第 8 题后直接显示第 10 题，本次没有发现第 9 题，因此按原文件实际编号继续，不虚构第 9 题。

原资料概念

资料把 LangChain 定义为 LLM 应用开发框架，用统一组件把模型、数据源、外部 API、工具、对话等组合起来，解决模型不了解私有实时数据、不能直接执行外部操作、复杂应用编排繁琐等问题。

核心功能

Model abstraction
Prompt / structured output
RAG / retriever
Tools / Agent
Memory / conversation
Workflow / chain
Observability / evaluation（生态层）

为什么

如果直接对接每一家模型 SDK，需要自己处理不同请求格式、工具调用、Embedding、向量检索、消息历史、结构化输出。框架提供统一抽象与可组合组件，让业务代码聚焦 AI 能力如何进入业务。

Java / Spring AI 化

LangChain 常见能力Spring AI / Java 对应
LLM / Chat ModelChatModel、ChatClient
Prompt / Output ParserPromptTemplate、Structured Output
RAG / RetrieverVectorStore、RAG Advisors
Tools@Tool、ToolCallback、Tool Calling
MemoryChatMemory + Advisors
外部协议/工具接入MCP Client / Server
复杂业务编排Spring Service / 状态机 / Workflow + Spring AI

    .system("你是企业数据助手")
    .user(question)
    .tools(databaseTools)
    .advisors(ragAdvisor)
    .call()
    .content();

AI补充/纠错

纠错：原资料把 LangChain 通俗描述为“API 套壳”，过于简单。框架真正价值不仅是封装 API，而是模型抽象、工具调用、RAG、状态/编排、结构化输出和生态集成。
Java 化：对于 Spring Boot 项目，不需要为了 RAG/Tool Calling 强制增加 Python + LangChain；Spring AI 已能承担大量常见 AI 应用基础能力。只有模型训练、PyTorch/Transformers、自研推理等 Python 优势明显的部分，再拆 Python 服务更合理。

常见坑

  • 以为用了框架就自动解决幻觉、权限和可靠性。
  • 业务逻辑全部塞进 Prompt，缺少 Java 侧确定性约束。
  • 为了“AI 技术栈”无必要增加跨语言微服务。
面试口述版：LangChain 的价值是把模型、Prompt、RAG、Tool、Memory 和工作流等 LLM 应用能力组件化，减少直接对接各种模型和外部数据源的重复工程。我的 Java 技术栈会优先用 Spring AI，对应使用 ChatClient、VectorStore、RAG Advisor、@Tool、ChatMemory 和 MCP；复杂业务状态仍放在 Spring Service 或 Workflow 层，而不是全部交给 Prompt。
