复习 1｜JVM 堆与 G1

先回答：经典 Eden/S0/S1/Old 模型和现代 G1 的 Region 模型有什么区别？为什么不能把“Eden 满→Minor GC→S0/S1→Full GC”当成所有现代 JVM 的固定流程？

答完后展开

经典分代模型强调连续的年轻代/老年代和 Survivor 复制；G1 则把堆划分为多个 Region，Eden、Survivor、Old 是 Region 的动态角色，年轻代大小和回收集合会根据暂停目标与运行状态调整。

面试口述版：经典分代模型便于理解对象生命周期，但现代 G1 是 Region 化、自适应的。面试时我会用 Eden/Survivor/Old 解释分代理念，再主动补充 G1 不按固定连续区域工作，GC 触发与回收集合也更动态。

复习 2｜JDK 11+ 堆比例

先回答：Young:Old=1:2、Eden:S0:S1=8:1:1 是不是 JDK 11+ 的固定规则？

答完后展开

不是。这些更像经典收集器的入门经验值。现代 G1 会动态调整年轻代 Region 数量，真实比例取决于 GC 算法、暂停目标、分配速率与工作负载。

复习 3｜JVM 参数

先回答：生产最常见的 JVM 参数类别有哪些？为什么现代 GC 日志更推荐 -Xlog:gc*？

答完后展开

常见关注堆（Xms/Xmx）、栈（Xss）、GC、Metaspace 和诊断日志。JDK 9+ 统一日志系统用 -Xlog 统一控制 GC 等运行日志，旧式 PrintGCDetails 已不适合作为现代推荐答案。

复习 4｜AI 工具链

先回答：如果主技术栈是 Spring Boot + Spring AI，哪些能力可以留在 Java 侧？什么时候才值得拆 Python 服务？

答完后展开

模型调用、RAG、Embedding、VectorStore、Tool Calling、Memory、MCP 等都可以留在 Spring AI；需要 PyTorch/Transformers、自研模型训练或强 Python AI 生态时再拆 Python 服务更合理。

复习 5｜Python 虚拟环境到 Java 的映射

先回答：Python venv 主要解决什么问题？Java 为什么通常不需要一套完全相同的 venv？

答完后展开

venv 解决依赖隔离和环境复现。Java 依靠 Maven/Gradle 的项目依赖、BOM、Wrapper、固定 JDK 与容器共同保证可重复构建和运行。

间隔复习｜约 3 天前：ThreadPoolExecutor

为什么任务进入线程池通常是 core → queue → max → reject，而不是先扩到 maximumPoolSize？

答完后展开

ThreadPoolExecutor 的设计优先稳定核心 worker 数，再使用队列吸收短时波动；只有队列不能再接收任务时才扩到 maximumPoolSize，最后触发拒绝策略。

间隔复习｜约 7 天前：Java 代理

JDK 动态代理和类代理的核心差异是什么？为什么 Spring AOP / @Transactional 会涉及代理？

答完后展开

JDK 动态代理主要基于接口生成代理；类代理通过子类化目标类实现。Spring AOP 在代理对象边界织入事务、日志、安全等横切逻辑，因此绕过代理的自调用可能让某些 Advice 不生效。

② 新题 1｜JDK 8 之后的方法区与 Metaspace 是什么关系？

原资料：《后端高频面试题大集合》JVM 第 6 题“介绍下JDK8之后的方法区实现和元空间的联系”｜PDF 第 42 页。正式后端 #32。

概念

方法区首先是 JVM 规范层面的逻辑概念，用来描述类相关元数据、运行时常量等共享信息应该有一个逻辑存储区域；PermGen / Metaspace则是 HotSpot 在不同年代用于承载类元数据的具体实现策略。

JVM 规范概念：Method Area
        ↓ HotSpot 实现
JDK 7 及更早：PermGen（永久代）
JDK 8+：Metaspace（元空间，主要使用本地内存）

原理

JDK 8 移除 PermGen 后，HotSpot 把类元数据主要放到 native memory 中的 Metaspace。这样不再受固定永久代大小直接限制，但仍会受系统内存和 MaxMetaspaceSize 等约束。

为什么这么改

  • 降低 PermGen 尺寸难以估计带来的调优负担。
  • 让类元数据空间能够按需要提交和回收。
  • 配合类卸载，将对应 ClassLoader 的 metadata chunk 重新利用或归还系统。

实际项目怎么用

遇到 OutOfMemoryError: Metaspace 时，不要只机械增大 MaxMetaspaceSize，而要检查类数量、ClassLoader 数量、动态类生成与类卸载情况。

AI补充/纠错

纠错 1：不要简单说“方法区 = 元空间”。更准确是：方法区是规范概念，Metaspace 是 HotSpot JDK 8+ 对类元数据存储的实现机制。

纠错 2：“PermGen 在堆里、Metaspace 完全等于 native heap”也容易说过头。现代 HotSpot 的类元数据管理还涉及 Compressed Class Space 等区域；Java 25 官方 GC 调优文档明确说明类卸载时元数据块可以复用或返回 OS，且 MaxMetaspaceSize 约束 committed class metadata 空间。

常见坑

  • 把 Metaspace 和 Java Heap 混在一起看。
  • 以为 Metaspace 默认无限就不会 OOM。
  • 只加内存，不检查 ClassLoader 泄漏。
面试口述版：方法区是 JVM 规范中的逻辑区域，HotSpot 在 JDK 8 之前主要用 PermGen 承载类元数据，JDK 8 起改用 Metaspace，类元数据主要使用本地内存。这样减少了永久代固定大小的调优压力，但如果动态加载大量类或发生 ClassLoader 泄漏，仍然可能出现 Metaspace OOM。

③ 新题 2｜Metaspace 参数怎么配？什么情况会 OOM？

原资料：《后端高频面试题大集合》JVM 第 7 题“介绍下元空间配置参数和什么操作会出现元空间不足”｜PDF 第 43～44 页。正式后端 #33。

概念

参数作用
-XX:MetaspaceSize影响触发 metadata GC / 类卸载相关阈值的初始水位，不宜简单理解成“元空间初始容量”
-XX:MaxMetaspaceSize限制可提交的类元数据空间上限；默认通常不人为限制

原理

类的元数据与定义它的 ClassLoader 生命周期强相关。ClassLoader 可回收、类可以卸载时，对应 Metaspace chunk 才可能被释放或复用。因此 Metaspace OOM 的排查重点往往是“类是否越来越多”和“ClassLoader 为什么活着”。

应用运行
  ↓
持续创建新 ClassLoader / 动态生成新类
  ↓
旧 ClassLoader 仍被引用，无法回收
  ↓
对应 Class metadata 无法卸载
  ↓
Metaspace committed 持续增加
  ↓
达到上限 / 系统内存压力
  ↓
OutOfMemoryError: Metaspace

为什么会发生

典型高风险来源包括热部署/插件系统中 ClassLoader 泄漏、CGLIB/ByteBuddy 等动态类生成失控、脚本/JSP 编译不断产生新类、容器重复部署却残留旧加载器等。

实际项目怎么用

# 查看进程
jps

# 观察 JVM flags
jcmd <pid> VM.flags

# 看类加载统计
jcmd <pid> VM.classloader_stats
jcmd <pid> GC.class_histogram

AI补充/纠错

纠错 1：原资料把 MetaspaceSize 默认值写成固定 21MB，这不适合作为现代通用答案。Oracle Java 25 文档明确说明其默认值是平台相关，大约 12MB～20MB。

纠错 2：“大量反射”“大量 Spring 注解”本身不等于一定制造大量新 Class。真正占用 Metaspace 的关键是被加载/生成的类元数据与 ClassLoader 生命周期。反射只是可能伴随动态生成、代理或类加载，不应该直接等同于 Metaspace 泄漏。

常见坑

  • 发生 OOM 就一味增大 MaxMetaspaceSize。
  • 只看 heap dump，不看 ClassLoader 与类加载数量。
  • 把类多和 ClassLoader 泄漏混为一谈。
面试口述版：MetaspaceSize 更像控制 metadata GC 的初始阈值，MaxMetaspaceSize 控制元空间可增长上限。Metaspace OOM 常见原因不是简单“用了很多反射”，而是动态生成或加载大量类，尤其旧 ClassLoader 长期无法回收。排查时我会结合 classloader stats、类加载数量和 native memory，而不是只加参数。

④ 新题 3｜新版 JVM 类加载子系统怎么理解？

原资料：《后端高频面试题大集合》JVM 第 8 题“介绍新版JVM虚拟机的类加载子系统”｜PDF 第 44～46 页。正式后端 #34。

概念

类加载不是“把 .class 读进来”一步完成，而是一个生命周期：

Loading
  ↓
Linking
 ├─ Verification
 ├─ Preparation
 └─ Resolution
  ↓
Initialization

原理

  • Loading：找到类字节并创建对应 Class 表示。
  • Verification：检查字节码结构和类型安全约束。
  • Preparation：为 static 字段等准备运行时结构并赋默认值。
  • Resolution：把符号引用解析为运行时可直接使用的引用，具体时机可延迟。
  • Initialization：执行类初始化逻辑，如 static 字段显式赋值、static block。

内置 ClassLoader

Bootstrap ClassLoader
        ↑
Platform ClassLoader
        ↑
System / Application ClassLoader
        ↑
自定义 ClassLoader（常见情况）

Java 9 后，Extension ClassLoader 被 Platform ClassLoader 取代。父子关系主要是委托关系，并不是 Java 类继承关系。

为什么要父委托

通常一个 ClassLoader 在自己找类之前先委托 parent，这能减少同名核心类被重复/恶意替换的风险，也帮助形成相对一致的类身份。

实际项目怎么用

Spring Boot、应用服务器、插件框架、SPI、热部署出现 ClassNotFoundException、NoClassDefFoundError、类型明明同名却无法 cast 时，都应该想到 ClassLoader 边界。

AI补充/纠错

纠错 1：父委托不是一个永远严格的“树形算法”。Oracle 当前 ClassLoader 文档明确说明，通常会先委托 parent；模块系统和某些容器/插件场景可能存在更复杂的可见性和非严格层级委托。

纠错 2：“只有需要时才加载”是总体上的 lazy loading 思想，但加载、解析、初始化各阶段触发条件并不完全相同，不应把它们混成一个“使用时一次性完成”的动作。

常见坑

  • 把 Platform ClassLoader 说成 JDK 9 新增在 Platform 与 App 之间的另一个 PlatformLoader。
  • 以为父加载器是 Java 继承关系。
  • 不知道同名类由不同 ClassLoader 定义时，在 JVM 看来可以是不同类型。
面试口述版：类加载生命周期包括加载、链接和初始化，链接又分验证、准备、解析。现代 JDK 内置加载器主要是 Bootstrap、Platform 和 System/Application ClassLoader，通常采用父委托模式：先让 parent 查找，再由当前加载器尝试。Java 9 后 Platform ClassLoader 取代旧 Extension ClassLoader。生产中遇到插件、SPI、热部署或类冲突时，我会重点检查 ClassLoader 可见性与类身份。

⑤ 新题 4｜Agent 是怎么实现上下文记忆的？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.12“Agent 是怎么实现上下文记忆的？”｜PDF 第 24～25 页。

概念

Agent Memory 不等于“把全部聊天记录永远塞进 Prompt”。更合理的是分层：

短期记忆
→ 最近若干消息 / 当前任务状态

长期记忆
→ 用户偏好、历史事实、任务摘要等可跨会话信息

当前上下文
→ System Prompt + 相关 Memory + 最近消息 + Tool Result + Query

原理

短期记忆通常按 conversation/session 保存消息窗口，限制 Token 数；长期记忆则先提取值得保存的事实或摘要，再写入关系库/向量库。新请求到来时，只检索和当前任务相关的长期记忆，而不是全量加载。

写入：
对话 → Memory Manager → 重要信息提取 → DB / VectorStore

读取：
Query → Memory Retrieval → Relevant Memories
     + Recent Messages + Tool Results
     → LLM

为什么

  • 上下文窗口有限，历史越长成本和延迟越高。
  • 无关历史会造成 Context Rot 和注意力稀释。
  • 跨用户、跨会话 Memory 必须严格隔离。

Spring AI / Java 化

Spring AI 当前提供 ChatMemory 抽象用于消息记忆，内置 MessageWindowChatMemory 默认维护有界消息窗口，并通过 ChatMemoryRepository 支持 InMemory、JDBC、Redis、MongoDB 等存储。长期语义记忆则可额外组合 VectorStore / PostgreSQL。

ChatClient
  ├─ ChatMemory → 短期对话窗口
  ├─ VectorStore → 长期语义记忆
  ├─ PostgreSQL → 结构化用户事实
  └─ Tool Result → 当前任务临时上下文

AI补充/纠错

补充：原资料用 messages[-N:] 说明短期记忆是正确的基础思路，但真实系统还需要 token budget、摘要压缩、重要消息保护、TTL、冲突更新、session/user/tenant 隔离。

补充：不要把所有用户信息都长期写入向量库。稳定、需要精确更新的事实（如用户配置）更适合结构化数据库；需要语义检索的历史片段/摘要才更适合 VectorStore。

常见坑

  • 把 ChatMemory 当成“模型真的记住了”。
  • 跨用户复用同一 conversationId，导致数据串话。
  • 所有聊天都 Embedding，长期记忆越来越脏。
  • 历史冲突不做版本/时间优先级处理。
面试口述版：Agent Memory 我会分成短期和长期。短期保存最近消息和任务状态，并通过窗口或摘要控制 Token；长期只提取有价值的用户事实、偏好或历史摘要，分别落结构化数据库或 VectorStore。Spring AI 可以用 ChatMemory 做短期消息窗口，结合 VectorStore 做长期语义检索，同时必须按 user/session/tenant 做隔离。

⑥ 新题 5｜LangChain 的 Chain 和 Agent 有什么区别？Spring AI 怎么映射？

原资料：《AI大模型面试题-基础篇》第 13 题“请比较LangChain框架中的Chain和Agent的区别及应用场景”｜PDF 第 11～12 页。

概念

维度Chain / 固定 WorkflowAgent
流程代码预先决定步骤模型在运行中决定下一步
确定性高相对低
成本/延迟较容易预测可能多轮模型/Tool 调用
适用摘要、ETL、固定审核流程开放任务、动态工具选择、多步探索

原理

固定 Workflow：
输入 → Step A → Step B → Step C → 输出

Agent：
输入 → LLM 判断
       ├→ Tool A → Observation ┐
       ├→ Tool B → Observation ├→ 再判断
       └→ Final                ┘

为什么要区分

不是所有 AI 需求都应该做 Agent。流程固定时，让 Java 代码明确编排通常更稳定、更便宜、更容易测试；只有步骤确实需要运行时动态决定时，Agent 才值得增加复杂度。

实际项目怎么用

以自然语言查数据库为例：

固定 Workflow：
用户问题 → 表选择 → SQL 校验 → 执行 → 结果总结

Agent：
用户问题 → 自主判断是否查表结构/业务定义/数据库
         → 多轮调用不同 Tool
         → 汇总答案

AI补充/纠错｜Spring AI 视角

Java 化：固定 Chain 可以直接由 Spring Service、函数组合或 Workflow 显式编排；动态 Agent 则可用 ChatClient + @Tool + Tool Calling Loop，再补 maxIterations、timeout、ACL、状态与审计。

工程原则：能用确定性 Workflow 解决的，不要为了“Agent 化”强行让模型决定每一步。

常见坑

  • 把 Chain 理解成“旧技术”、Agent 一定更高级。
  • 固定业务流程也交给 Agent，导致不可预测。
  • Agent 没有限制迭代次数和 Tool 权限。
面试口述版：Chain 更像预定义流程，步骤由程序提前决定，适合摘要、数据转换等确定性任务；Agent 则让模型根据当前状态动态选择工具和下一步，适合开放、多步骤问题。Java/Spring AI 项目中，固定流程我优先由 Spring Service 显式编排，需要动态决策时再使用 ChatClient 的 Tool Calling 能力，并增加迭代、权限、超时和审计控制。
