① 前一天复习｜先凭记忆回答

复习来源：2026-09-08 正式 Day 9。自动学习无法等待实时作答，因此答案放入折叠区；建议每题先口述 20～30 秒。未收到用户回答时不虚构“已掌握”评分。

复习 1｜池化思想

先回答：池化真正解决哪两个问题？为什么“池越大越好”是错误的？

答完后展开

池化主要解决昂贵资源的复用成本与资源总量边界。池太大会造成线程切换、连接竞争、内存占用和下游压力，参数应以任务类型、下游容量和压测为依据。

面试口述版：池化通过复用昂贵资源减少创建销毁成本，同时用容量边界限制资源总量。线程池、数据库连接池都不能无限放大，要结合 CPU、阻塞比例和下游承载能力配置。

复习 2｜ThreadPoolExecutor 任务进入顺序

先回答：为什么是“core → queue → max → reject”，而不是先扩到 maximumPoolSize？

答完后展开
线程数 < core → 新建 worker
否则 → 尝试入队
队列满 → 再扩到 maximumPoolSize
线程和队列都满 → reject

这样可以在并发线程数和排队长度之间做折中，避免一有突发请求就快速创建大量线程。

复习 3｜Executors 与虚拟线程

先回答：FixedThreadPool 为什么在高流量服务里有风险？VirtualThreadPerTaskExecutor 是否意味着数据库连接也可以无限多？

答完后展开

FixedThreadPool 使用无界队列，生产速度长期超过消费速度时会形成任务堆积；虚拟线程降低“线程本身”的成本，但 DB 连接、外部 API QPS 等下游资源仍然有严格上限。

复习 4｜Agent 核心瓶颈

先回答：为什么 Agent 的错误比普通 Chatbot 更危险？至少说出 4 个投产瓶颈。

答完后展开

Agent 会执行真实动作，推理错误可能变成错误 Tool Call 并级联传播。高频瓶颈包括可靠性、Planning、成本与延迟、长上下文退化、安全、评测、可观测性。

复习 5｜LangChain → Spring AI

先回答：在 Java 项目里，LangChain 的 Model / RAG / Tool / Memory 大致分别映射到 Spring AI 什么能力？

答完后展开

Model → ChatModel/ChatClient；RAG → VectorStore + RAG Advisor；Tool → @Tool/ToolCallback；Memory → ChatMemory；复杂业务 Workflow 继续由 Spring Service/状态机承担。

间隔复习｜约 3 天前：ThreadLocal

为什么 Key 是弱引用仍然要 finally remove()？

答完后展开

Key 变 null 后 Value 仍可能由 ThreadLocalMap 强引用，线程池线程长期存活会造成 stale entry 滞留和上下文串请求。

间隔复习｜约 7 天前：ConcurrentHashMap

为什么现代 Java 面试不能只回答“分段锁”？

答完后展开

Segment 分段锁主要对应 JDK 7；JDK 8+ 主体结构改为 Node[] + 链表/红黑树，并结合 CAS 与 synchronized 控制局部更新。

② 新题 1｜生产环境事故分析：线程池使用选择问题

原资料：《后端高频面试题大集合》JUC 第 13 题“生产环境事故分析-线程池使用选择问题”｜PDF 第 34～35 页。正式后端 #26。

概念

这题考的不是“会不会 new ThreadPoolExecutor”，而是能否从吞吐、排队延迟、线程数、队列长度、拒绝策略和下游容量一起分析线程池事故。

原理

原资料案例中，商品详情页用 CompletableFuture 并行聚合基础信息、库存、活动等接口，但线程池配置成很小的 corePoolSize + 极大的 ArrayBlockingQueue。高峰时任务大量排队，因为队列一直没满，maximumPoolSize 几乎没有机会发挥。

corePoolSize = 2
maximumPoolSize = 32
queue = 100000

高并发到来
→ 2 个核心线程忙
→ 大量任务进入超长队列
→ maxPoolSize 很难被触发
→ 排队时间不断增加
→ 接口超时

为什么

线程池设计本质是三种压力的平衡：更多线程可降低排队，但会增加 CPU 调度和下游并发；更大队列可吸收突发，但会增加尾延迟和内存；更早拒绝则牺牲部分请求换取系统整体稳定。

实际项目怎么用

AI 调用池       → 限制外部模型并发/QPS
文件解析池      → CPU/IO 混合，避免挤占请求线程
DB 分析池       → 上限不能超过连接池和数据库承载
推送/网络池     → IO 型，但仍要限流

监控至少包括 activeCount、poolSize、queueSize、completedTaskCount、reject count、task wait time、task execution time。

AI补充/纠错

纠错：原资料建议“队列不要过大、调高 core/max”方向有价值，但不能机械照抄成固定解法。真正正确的是先看下游容量、CPU、阻塞比例和 SLA。若 DB 只有 20 个可用连接，把线程池从 32 拉到 256 反而可能让系统更差。

纠错：DiscardPolicy 在核心业务上非常危险，因为任务会静默丢弃。生产环境通常更希望可观测地拒绝、降级或 CallerRuns 形成背压。

常见坑

  • 只盯 maximumPoolSize，忘记大队列会让它很难生效。
  • 只看平均 RT，不看 p95/p99 和 queue wait time。
  • 不同业务共用同一线程池，某一类慢任务拖垮全部异步任务。
  • 拒绝策略静默丢任务却没有指标和日志。
面试口述版：线程池事故我会先看 active threads、queue size、任务等待时间、拒绝数和下游容量。ThreadPoolExecutor 是 core 满后先入队，队列满才扩到 maximumPoolSize，所以过大的队列会造成大量排队、让 maxPoolSize 失去意义。修复不是单纯加线程，而是根据 CPU、阻塞比例、数据库连接数和外部 API QPS 重新配置，并对不同业务做线程池隔离和拒绝/降级监控。

可能追问

为什么 CallerRunsPolicy 有背压效果？如何估算队列长度？线程池和数据库连接池应该怎样匹配？

③ 新题 2｜什么是 JVM？常见实现有哪些？

原资料：《后端高频面试题大集合》JVM 第 1 题“什么是Java虚拟机，常见的版本有哪些？”｜PDF 第 35～36 页。正式后端 #27。

概念

JVM（Java Virtual Machine）是执行 Java 字节码的虚拟机规范与运行时实现。Java 源码由 javac 编译成 .class 字节码，再由 JVM 负责类加载、执行、内存管理、JIT 编译、GC、线程与运行时安全。

.java
  ↓ javac
.class bytecode
  ↓
JVM
├─ Class Loading
├─ Runtime Data Areas
├─ Interpreter / JIT
├─ GC
└─ Native Interface
  ↓
OS / CPU

原理

“一次编译、多平台运行”的关键不是 JVM 自己跨平台，而是字节码相对平台中立，每个平台提供自己的 JVM 实现。

常见实现

实现今天怎么理解
HotSpotOpenJDK/Oracle JDK 最常见的 JVM 实现，面试主线通常默认它。
Eclipse OpenJ9来自 IBM J9 技术路线的开源 JVM，强调较低内存占用、快速启动等场景。
GraalVM基于 Java 平台并提供 Graal 编译器、Native Image、多语言能力；既可作为 JVM/JDK 发行体系，也常用于 AOT Native Image。

为什么

理解 JVM 实现差异有助于解释 GC、JIT、启动速度、内存占用、容器部署与 Native Image 的差异。日常 Java 面试多数以 HotSpot 为主，不需要把历史 JVM 名单全部背下来。

实际项目怎么用

Spring Boot 常规服务器通常运行在 HotSpot；若追求极快启动和较小内存，可评估 GraalVM Native Image；特殊企业环境可能选择 OpenJ9。

AI补充/纠错

截至 2026-09：Eclipse OpenJ9 仍在活跃发布，2026 年 8 月的 0.61.0 支持 OpenJDK 8/11/17/21/25/26；GraalVM 也持续基于 JDK 25 演进。因此原资料把 JRockit、J9 当作“当前常见实现”的历史列表需要更新：JRockit 更适合作为历史背景，现代回答优先 HotSpot、OpenJ9、GraalVM。

常见坑

  • 把 JDK、JRE、JVM 三者混为一谈。
  • 说 JVM 让 Java 源码直接跨平台；真正跨平台的是统一字节码 + 各平台 JVM。
  • 背历史 JVM 名称但不会解释 HotSpot 的类加载、JIT 和 GC。
面试口述版：JVM 是执行 Java 字节码的运行时，它负责类加载、字节码执行、JIT、内存管理和 GC。Java 通过编译成相对平台无关的字节码，再由不同操作系统上的 JVM 执行来实现跨平台。现代项目最常见的是 HotSpot，另外还有 Eclipse OpenJ9 和 GraalVM 等实现或运行时体系。

可能追问

JDK/JRE/JVM 区别？解释执行和 JIT 什么关系？GraalVM Native Image 还算 JVM 运行吗？

④ 新题 3｜JVM 运行时内存的 5 大组成

原资料：《后端高频面试题大集合》JVM 第 2 题“说下JVM内存的5大组成部分(基于JDK8以上的HotSpot虚拟机)”｜PDF 第 36～37 页。正式后端 #28。

概念

区域线程关系核心作用
程序计数器线程私有记录当前线程执行到的字节码位置
Java 虚拟机栈线程私有每次 Java 方法调用创建栈帧，存局部变量表、操作数栈、返回信息等
本地方法栈线程私有服务 native 方法调用；具体实现可与虚拟机栈合并
堆 Heap线程共享绝大多数对象和数组分配区域，GC 的主要管理对象
方法区（HotSpot JDK8+ 常由 Metaspace 承载类元数据）线程共享类结构、运行时常量池等类级信息

原理

Thread A
├─ PC
├─ Java Stack
└─ Native Stack

Thread B
├─ PC
├─ Java Stack
└─ Native Stack

Shared
├─ Heap
└─ Method Area / class metadata (HotSpot: Metaspace)

为什么

不同区域有不同生命周期和错误类型：线程栈过深可能 StackOverflowError；线程创建过多或 native 内存不足可能影响栈分配；堆不足会出现 Java heap space；Metaspace 受限且类元数据不断增长时可能 Metaspace OOM。

实际项目怎么用

排查问题时先根据异常类型判断区域：大量对象/缓存看 Heap；动态生成类、ClassLoader 泄漏看 Metaspace；递归和巨大栈帧看 Java Stack；直接内存、线程数还要看堆外 native memory。

AI补充/纠错

纠错：原资料把“元数据区”直接等同于五大运行时区域之一，面试时最好说规范里的方法区，然后补充 HotSpot 自 JDK 8 起用本地内存中的 Metaspace 实现类元数据存储。

补充：“JVM 内存只有这 5 块”也不够严谨。直接内存、Code Cache、线程栈的 native backing、GC 结构等也占进程内存，只是经典面试题通常问 JVM 规范运行时数据区。

常见坑

  • 把“方法区”和“Metaspace”完全当成同一个规范概念。
  • 以为所有局部变量都在栈里、所有对象都一定只在堆里；JIT 逃逸分析可能优化实际分配。
  • 只看 -Xmx 就认为 JVM 进程总内存不会超过它。
面试口述版：经典 JVM 运行时数据区包括程序计数器、Java 虚拟机栈、本地方法栈、堆和方法区。前三者线程私有，堆和方法区线程共享。HotSpot 在 JDK 8 后使用 Metaspace 在本地内存中承载类元数据。排查 OOM 时还要注意 JVM 进程还有直接内存、Code Cache 等堆外内存，不能只看 Xmx。

可能追问

栈帧有哪些结构？方法区和永久代/元空间什么关系？为什么 RSS 可能远大于 -Xmx？

⑤ 新题 4｜近半年一年，大模型领域哪些进展最值得面试讲？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.10“近半年一年大模型领域有哪些让你印象深刻的技术或产品进展？”｜PDF 第 8～9 页。

概念

这是一道时效性开放题。面试官不是要你背发布会，而是看你能否把最近技术变化归纳成对工程开发有意义的趋势。

原资料内容

资料把进展分为：模型能力跃迁、Agent 基础设施成熟、编码/通用 Agent 产品创新、行业生产落地等，并举了 GPT-5 系列、Claude、Gemini、DeepSeek、MCP、Microsoft Agent Framework、LangGraph、Claude Code/Cursor/Manus/Deep Research 等例子。

AI补充/纠错｜截至 2026-09-09 的推荐回答

不要死背资料中的榜单、上下文长度和百分比。这些会快速过期。今天更稳的 4 个趋势是：
1）Agentic coding 从“补全代码”走向“长任务执行”：OpenAI 在 2026-02-05 发布 GPT-5.3-Codex，明确定位专业工作与 agentic coding。
2）Agent 框架进入企业级稳定阶段：Microsoft Agent Framework 1.0 已于 2026-04-14 GA，融合 Semantic Kernel 与 AutoGen 的路线，并支持 MCP/A2A 等互操作。
3）企业 Agent 平台把安全、Tracing、Evaluation 变成基础设施：Microsoft Foundry Agent Service 在 2026-03 GA，突出 RBAC、私网、Tracing 和 Evaluation。
4）复杂 Agent 的竞争点从“能调用 Tool”转向“工作流、状态、可观测和治理”：这也是你学习 Spring AI 时要特别补的工程层。

原理

2024/早期：Chat → 文本
2025：Tool Calling → 能调用外部能力
2026：Agent Workflow → 长任务、状态、评测、权限、互操作、治理

为什么

模型能力提高后，企业落地的瓶颈逐渐从“模型会不会回答”转向“系统能不能可靠执行、出错能不能定位、权限能不能控制、成本能不能预测”。

实际项目怎么用｜Spring AI 视角

你自己的项目可以把趋势映射成：ChatClient 负责模型入口，@Tool/MCP 负责外部能力，ChatMemory/RAG 负责上下文与私有知识，Java Service 负责状态和审批，Observability 负责 trace/latency/token/tool result，数据库层做白名单与 ACL。

常见坑

  • 只报模型名字和 benchmark，不讲对工程有什么影响。
  • 把 MCP 说成“模型能力”；它本质是工具/上下文连接协议。
  • 把 Tool Calling 等同于完整 Agent。
  • 引用“最新榜单第一”却说不清日期，面试中很容易过时。
面试口述版：近一年我最关注的不是单一模型榜单，而是三类变化：第一，编码 Agent 已从补全发展到能执行长时间软件工程任务；第二，MCP、A2A 和企业 Agent Framework 让工具和 Agent 互操作逐渐标准化；第三，企业落地开始把权限、Tracing、Evaluation 和工作流治理当成基础设施。对 Java 开发者来说，这意味着 Spring AI 的 Tool/RAG/MCP 只是底层能力，真正拉开差距的是可靠编排和工程治理。

⑥ 新题 5｜LangChain 生态有哪些核心产品？Spring AI 怎么对应？

原资料：《AI大模型面试题-基础篇》第 11 题“LangChain生态系统包含哪些核心产品及其作用?”｜PDF 第 9～10 页。

原资料内容

资料列出 LangChain Core、LangServer、LangSmith、LangGraph，并尝试与 Spring AI、Spring Boot、Prometheus/Grafana、Activiti 做类比。

AI补充/纠错

纠错 1：资料里的“LangServer”应是 LangServe。LangServe 用于把 LangChain Runnable/Chain 暴露成 REST API。

纠错 2（时效性很重要）：LangServe 已从 2024-11 起 Deprecated，GitHub 仓库在 2026-05-05 归档；官方建议新项目迁移到 LangGraph Platform / LangSmith Deployment，因此今天面试不要把 LangServe 当成 LangChain 的主力新产品。

纠错 3：“LangSmith = Prometheus + Grafana”只是非常粗糙的类比。LangSmith 不只做系统指标，还覆盖 LLM/Agent trace、数据集、evaluation、prompt/agent 调试等 AI 特有可观测能力。

纠错 4：“LangGraph = Activiti BPMN”也只是帮助理解状态工作流；LangGraph 是面向 LLM/Agent 的 stateful graph orchestration，不等同于 BPMN 流程引擎。

今天建议记的生态结构

LangChain 生态作用Java / Spring AI 对应理解
LangChain模型、Prompt、Tool、Retriever 等应用抽象ChatClient / ChatModel / Prompt / @Tool / VectorStore
LangGraph有状态、多步骤、可中断/恢复的 Agent WorkflowSpring Service + 状态机/工作流；Spring AI 提供底层 AI 能力
LangSmithTracing、Evaluation、Datasets、Agent 调试与部署治理Micrometer/OTel + 自建 Eval/Trace；能力并非一一对应
LangGraph Platform / LangSmith DeploymentAgent 服务部署和运行Spring Boot/Vercel/容器平台 + 自己的运行时治理

原理

模型调用抽象：LangChain
        ↓
复杂有状态编排：LangGraph
        ↓
调试 / 评测 / Trace / 部署：LangSmith / Platform

为什么

随着 Agent 变复杂，单纯“Chain API”已经不足，需要显式状态、暂停/恢复、人工审批、长任务和可观测。因此生态自然从模型抽象层延伸到 Agent runtime 和 observability。

实际项目怎么用｜Java 化

你没有必要为了模仿 LangChain 全家桶强行增加 Python 层。对于 Next.js + Spring Boot 项目，可以用 Spring AI 提供模型/RAG/Tool/MCP，Java 服务层管理状态与工作流，OpenTelemetry/Micrometer + DB 表记录 tool call、token、latency、result、error；当确实需要 Python 特有 Agent 生态时再拆服务。

常见坑

  • 把 LangChain、LangGraph、LangSmith 当成同一个库。
  • 继续回答“LangServe 是核心部署方案”而不知道它已 Deprecated。
  • 把 LangGraph 说成纯粹的多 Agent 框架；核心更准确是 stateful graph/workflow runtime。
面试口述版：现在 LangChain 生态可以理解为三层：LangChain 提供模型、Prompt、Tool、Retriever 等应用抽象；LangGraph 负责有状态的 Agent Workflow；LangSmith 负责 Trace、Evaluation、Datasets 和运行治理。旧的 LangServe 已 Deprecated 并在 2026 年归档，新项目不应再把它作为主力部署方案。Java 项目里我会优先用 Spring AI 对应模型、RAG、Tool 和 MCP，复杂流程和可观测性由 Spring 服务层继续补齐。
