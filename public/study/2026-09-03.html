复习题 1｜ConcurrentHashMap 为什么不能只回答“分段锁”？

请先回答：JDK 7 与 JDK 8+ 的核心实现差异是什么？为什么它通常比 Hashtable 并发性能更好？

答完后展开：纠错 + 面试口述版

纠错：“分段锁”主要对应 JDK 7。JDK 8+ 取消 Segment 主体结构，使用 Node 数组，并结合 CAS、synchronized 等控制局部更新。

面试口述版：Hashtable 同步粒度较粗；ConcurrentHashMap 在 JDK 7 使用 Segment 分段锁，JDK 8+ 改为 Node 数组加 CAS 和 synchronized 控制局部更新，因此竞争范围更小、并发度更高。

复习题 2｜Java 泛型最核心的价值是什么？

请先回答：泛型解决什么问题？什么是类型擦除？为什么 List<String> 不是 List<Object> 的子类型？

答完后展开：纠错 + 面试口述版

泛型的核心价值是编译期类型安全，同时减少强转、提高 API 可读性和复用性。Java 普通泛型主要通过类型擦除实现。

面试口述版：Java 泛型是参数化类型，把很多类型错误从运行期提前到编译期。它主要通过类型擦除实现，所以很多具体泛型参数不会以普通 Class 形式保留在运行时。

间隔复习｜约 3 天前：HashMap 什么时候树化？

《后端高频面试题大集合》JAVASE 核心，第 2 题｜HashMap 数组 + 链表 + 红黑树。

请先回答：链表达到 8 个节点是不是一定立刻树化？

答完后展开

不是。JDK 8 中除了链表长度阈值，还要看 table 容量；容量不足 64 时通常优先扩容。常见常量：TREEIFY_THRESHOLD=8，UNTREEIFY_THRESHOLD=6，MIN_TREEIFY_CAPACITY=64。

② 当天新知识 1｜Java 泛型常见通配符

原资料：《后端高频面试题大集合》JAVASE 核心，案例 10｜“说下 java 泛型常见的通配符有哪些”｜PDF 约第 8 页。原资料列出 ?、extends、super；其中示例语法存在不严谨之处。

概念

写法含义典型用途
List<?>未知类型只关心“这是某种 List”
List<? extends Number>Number 或其子类主要读取
List<? super Integer>Integer 或其父类主要写入 Integer

原理 / 为什么

Java 泛型是不协变的：即使 Integer extends Number，也不能把 List<Integer> 直接赋给 List<Number>。通配符用来描述“可接受的一组泛型类型”。

List<Integer> ints = List.of(1,2,3);
List<? extends Number> nums = ints; // OK

Number n = nums.get(0);  // 可安全读取
// nums.add(1);          // 编译不允许：实际类型可能是 Double

AI补充/纠错｜PECS

原资料纠错：泛型下界语法是 ? super A，不是 T supers A。另外 T extends A 属于“类型参数上界”，和通配符 ? extends A 概念相关但不是同一种语法。

高频口诀：PECS = Producer Extends, Consumer Super。

// 从 src 读取 T：Producer → extends
static <T> void copy(List<? extends T> src,
                     List<? super T> dest) {
    for (T x : src) dest.add(x);
}

实际项目怎么用

公共组件、集合工具类、框架 API 中很常见。你写业务 CRUD 时不一定天天手写，但看 Spring / JDK API 时必须能读懂。

常见坑

  • ? extends T 不是“完全不能写”，但通常不能安全写入具体 T；null 除外。
  • ? super T 读取时只能安全当 Object 使用。
  • 不要把 <T extends A> 与 <? extends A> 混为一谈。
面试口述版：Java 泛型常见通配符有无界通配符 ?、上界 ? extends T 和下界 ? super T。上界适合从集合中读取，下一般用于向集合写入，因此常用 PECS 记忆：Producer Extends、Consumer Super。

③ 当天新知识 2｜Agent 的工作模式有哪些？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.4｜“Agent 的工作模式都有什么？”｜PDF 第 3～4 页。原资料包括 ToolsCallingAgent、ReAct、Reflection、PlanAndSolve、Multi-Agent、Human-in-the-Loop。

概念

模式核心适合
Tool Calling模型直接选工具简单单步任务
ReAct推理→行动→观察循环动态多步任务
Reflection生成后自检再修正高准确性任务
Plan-and-Solve先计划后执行步骤明确的复杂任务
Multi-Agent多个专业 Agent 协作复杂分工
Human-in-the-Loop关键节点人工批准高风险动作

原理 / 为什么

不是所有任务都应该上最复杂 Agent。复杂度越高，通常意味着更多模型调用、更高延迟、更多状态管理和更难调试。应从最简单可用模式开始。

AI补充/纠错｜Spring AI 视角

Spring AI 2.0 的 Tool Calling Loop 由 ChatClient 中的 ToolCallingAdvisor 驱动，ToolCallingManager 执行工具。这能很好承载 Tool Calling / 部分 ReAct 风格循环，但 Reflection、全局 Planning、Multi-Agent、人工审批仍通常需要额外的 Java Workflow / 状态控制。

String answer = chatClient.prompt()
    .user("查询订单并判断是否需要人工审批")
    .tools(orderTools)
    .call()
    .content();

// 高风险动作：业务层仍应做显式权限/审批控制，
// 不应只因为模型请求 Tool 就直接执行。
版本确认：Spring AI 2.0 官方文档将 Tool Calling Loop 作为 ChatClient Advisor Chain 的一等组件；模型只“请求”工具，真正执行由应用程序负责。

实际项目怎么用

数据库查询助手可以先从 Tool Calling 开始；需要连续查多张表再归因时可引入 ReAct/Planning；涉及退款、发邮件、改生产数据时应加入 Human-in-the-Loop。

常见坑

  • Tool Calling ≠ 完整 Agent。
  • Multi-Agent 不是越多越高级，通信与状态一致性成本很高。
  • 不要让模型绕过业务权限直接执行高风险 Tool。
面试口述版：Agent 常见模式有 Tool Calling、ReAct、Reflection、Plan-and-Solve、Multi-Agent 和 Human-in-the-Loop。选型原则是从简单模式开始，只有任务确实需要多步规划、自我校验或多人协作时再增加复杂度。在 Spring AI 中 ToolCallingAdvisor 能承载标准工具循环，复杂规划与审批通常由 Java 服务层继续编排。

④ 当天新知识 3｜为什么技术人员也要会写产品需求文档（PRD）？

原资料：《AI大模型面试题-基础篇》第 4 题｜“作为技术人员，为什么需要掌握产品需求文档的编写？”｜PDF 第 3～4 页。

概念

PRD 不是“产品经理专属文档”，它用于把业务目标、用户场景、功能范围、约束和验收标准变成研发可执行的共同语言。

原资料内容

  • 技术人员更了解实现复杂度和可行性。
  • 能更准确评估技术风险与需求优先级。
  • AI 项目还要考虑模型性能与限制、数据安全与隐私、训练/部署资源。

AI补充/纠错｜AI 项目的 PRD 要比普通 CRUD 多写什么？

普通功能常写AI 功能额外必须明确
用户、流程、字段、权限、验收条件模型能力边界 / 不保证事项
接口与异常流程幻觉容忍度、人工兜底
性能要求延迟、Token/调用成本预算
数据权限RAG 数据源、ACL、敏感数据处理
成功标准准确率/召回率/任务成功率/人工接管率等评估指标

实际项目怎么用

以“自然语言查数据库”功能为例，PRD 不应该只写“用户输入问题，AI 返回数据”，还要明确：允许查哪些表、是否只读、最大返回行数、敏感字段如何脱敏、SQL 失败怎么处理、模型无法确认时是否拒答、执行前是否需要二次确认。

需求：AI 查询数据库

必须明确：
1. 只允许 SELECT
2. 表/字段白名单
3. 用户权限映射
4. 最大查询行数 / 超时
5. SQL 审计日志
6. 不确定时禁止执行
7. 高风险查询需要人工确认

常见坑

  • PRD 只写 Happy Path，不写失败和降级。
  • 把“回答准确”写成模糊目标，却没有可测指标。
  • 忽略 AI 的概率性，把它当传统确定性 API。
面试口述版：技术人员掌握 PRD 能更早识别可行性、技术风险和边界条件，减少产品与研发之间的信息损耗。AI 项目尤其需要技术人员参与，因为除了普通功能需求，还必须明确模型能力边界、数据隐私、RAG 权限、幻觉兜底、延迟成本以及可量化的效果指标。
