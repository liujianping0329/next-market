复习 1｜反射：Class.newInstance() 为什么不再推荐？

先回答：现代 Java 通过反射创建对象推荐什么写法？getMethods() 和 getDeclaredMethods() 有什么区别？

答完后展开：纠错 + 口述版

Class.newInstance() 从 Java 9 起已 Deprecated，推荐 clazz.getDeclaredConstructor().newInstance()。getMethods() 返回 public 方法并包含继承的方法；getDeclaredMethods() 返回当前类声明的方法，不要求 public，但不包含继承来的方法。

面试口述版：反射通过 Class 获取构造器、方法、字段等运行时元数据。现代 Java 反射创建对象推荐 getDeclaredConstructor().newInstance()；Java 9+ 模块系统也限制了任意深反射访问。

复习 2｜元注解：Retention 为什么最容易被追问？

先回答：SOURCE、CLASS、RUNTIME 有什么区别？如果要通过 Spring/AOP 在运行时读取自定义注解应该选哪个？

答完后展开

RetentionPolicy.RUNTIME 会保留到 JVM 运行期，才能通过反射读取。SOURCE 只存在源码阶段，CLASS 会进字节码但运行期不保证可反射获取。

复习 3｜代理：JDK 动态代理和类代理的核心差别？

先回答：JDK 动态代理对目标对象有什么要求？Spring AOP 为什么和 @Transactional 有关系？

答完后展开

JDK 动态代理基于接口；类代理通过生成目标类子类实现增强。Spring AOP 常通过代理拦截 Bean 方法，在调用前后织入事务、日志、权限等逻辑；因此同类内部自调用可能绕过代理。

复习 4｜Agent 设计范式

先回答：ReAct、Reflection、Planning、Sequential Workflow、Multi-Agent、Human-in-the-Loop 分别解决什么问题？

答完后展开

ReAct 解决动态推理+行动；Reflection 做自检修正；Planning 先全局拆任务；Sequential Workflow 强确定性流水线；Multi-Agent 做角色分工；Human-in-the-Loop 用于高风险审批节点。

复习 5｜外部 LLM API 与 GPU

先回答：Spring Boot 调 OpenAI/通义/Anthropic 等外部模型 API 时，自己的应用服务器是否必须有 GPU？什么时候 GPU 才成为直接资源需求？

答完后展开

调用外部模型 API 时，推理算力由模型供应商承担，Spring Boot 服务器通常不需要 GPU。自托管 LLM、本地 Embedding/Reranker、模型训练/微调等场景才需要直接评估 GPU/显存。

间隔复习｜约 3 天前：HashMap 什么时候树化？

先回答：一个 bucket 链表长度达到 8 时，是不是一定马上转红黑树？

答完后展开

不是。JDK 8 中还要看 table capacity；当容量小于 64 时通常优先扩容，达到最小树化容量后才考虑树化。常见常量：TREEIFY_THRESHOLD=8，UNTREEIFY_THRESHOLD=6，MIN_TREEIFY_CAPACITY=64。

② 新题 1｜Java 并发中常见的锁有哪些？

原资料：《后端高频面试题大集合》JUC 并发编程，第 1 题“你知道多少种并发编程常见的锁”｜PDF 第 15～16 页。正式总进度记为后端 #14。

概念

这题不是让你背“锁类名大全”，而是考察你能否从不同维度理解并发控制：悲观/乐观、公平/非公平、独享/共享、可重入/不可重入、自旋，以及锁粒度设计。

分类维度概念Java 示例
悲观 / 乐观先锁住再操作 / 先操作并在更新时检测冲突synchronized、ReentrantLock / CAS、版本号
公平 / 非公平尽量按排队顺序获取 / 允许新线程插队竞争ReentrantLock(true/false)
独享 / 共享同一时刻一个线程 / 多线程可共享读写锁 / ReentrantReadWriteLock.ReadLock
可重入同一线程持锁后可再次进入同一锁保护区synchronized、ReentrantLock
自旋不立即阻塞，短时间循环等待状态变化CAS 重试等

原理

悲观：先取得互斥权 → 再修改
乐观：读取旧值 → CAS/版本比较 → 成功则更新，失败则重试或放弃

公平：队列前驱优先
非公平：新线程可先尝试抢锁，失败再进入/遵循等待队列

为什么

不同冲突概率、临界区长度和吞吐目标需要不同策略。竞争激烈且写多时，阻塞式互斥可能更稳；临界区很短、冲突低时，CAS/自旋可能减少线程挂起与唤醒成本。

实际项目怎么用

private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

rw.readLock().lock();
try {
    return cache.get(key);
} finally {
    rw.readLock().unlock();
}

AI补充/纠错

纠错 1：“悲观锁适合写多、乐观锁适合读多”只能作为粗略经验，真正要看冲突概率和临界区成本。
纠错 2：“分段锁”更准确地说是锁粒度设计思想，而不是 Java 中一个具体 Lock 类型。原资料把 ConcurrentHashMap 与分段锁绑定，需要加版本条件：这是 JDK 7 的典型 Segment 设计，JDK 8+ 已改变。

常见坑

  • CAS 严格说是原子操作机制，不是一个 Lock 对象。
  • 自旋不是越久越好，竞争时间长时会白白烧 CPU。
  • 公平性通常会牺牲一部分吞吐量。
面试口述版：Java 的锁可以从多个维度理解，比如悲观/乐观、公平/非公平、独享/共享、可重入和自旋。synchronized、ReentrantLock 属于典型悲观互斥；CAS 是乐观并发控制基础。锁的选择要看冲突概率、临界区长度和吞吐目标，而不是机械地选某一种。

③ 新题 2｜ReentrantLock 是公平锁还是非公平锁？为什么默认这样设计？

原资料：《后端高频面试题大集合》JUC 并发编程，第 2 题“ReentrantLock是公平锁还是非公平锁，为什么这样设计”｜PDF 第 16～17 页。正式总进度记为后端 #15。

概念

ReentrantLock 两种都支持：

new ReentrantLock();      // 默认非公平
new ReentrantLock(false); // 非公平
new ReentrantLock(true);  // 公平

原理

底层基于 AQS。公平模式获取锁前会检查等待队列前面是否已有线程；非公平模式允许新线程先直接尝试 CAS 抢占，抢不到再进入 AQS 排队。

公平：   先看队列 → 前面有人就排队 → 尽量先来先得
非公平： 新线程先抢一次 → 成功就直接进入 → 失败再排队

为什么默认非公平？

因为刚释放锁时，正在运行的线程或新到线程若能直接取得锁，可以减少线程挂起、唤醒和上下文切换的机会，通常能获得更高吞吐。

实际项目怎么用

普通业务优先默认非公平；如果业务对“长期等待/饥饿”特别敏感，比如需要更强排队公平性的调度场景，再考虑公平锁。

AI补充/纠错

重要纠错：原资料把“非公平锁”写成“随机获取”并不准确。非公平不是随机，而是允许 barging（插队竞争）。另外，非公平锁也不是“完全没有阻塞和恢复步骤”；抢锁失败后仍会进入 AQS 队列并可能阻塞。

常见坑

  • 公平锁不是绝对严格实时顺序保证，它是基于同步队列的公平获取策略。
  • tryLock() 的语义与普通 lock() 公平策略要区分。
  • 公平 ≠ 性能更好；一般恰恰相反。
面试口述版：ReentrantLock 既支持公平也支持非公平，通过构造参数选择，默认是非公平。公平模式会优先尊重 AQS 等待队列；非公平模式允许新线程先尝试抢锁，因此减少一部分线程切换成本，通常吞吐更高，所以被设计为默认。

④ 新题 3｜什么是对象锁和类锁？

原资料：《后端高频面试题大集合》JUC 并发编程，第 3 题“说下什么是对象锁和类锁，使用场景有什么差异点”｜PDF 第 18 页起。正式总进度记为后端 #16。

概念

对象锁锁的是某个实例对象的 monitor；类锁锁的是该类对应的 Class 对象。

public synchronized void instanceMethod() {
    // 等价于 synchronized(this)
}

public static synchronized void staticMethod() {
    // 锁的是 MyService.class
}

synchronized (MyService.class) {
    // 类锁
}

原理

new MyService() -> 实例 A monitor
new MyService() -> 实例 B monitor
MyService.class -> Class 对象 monitor

A 的对象锁 与 B 的对象锁：不同
对象锁 与 类锁：也不同

为什么

同步范围取决于共享资源范围。如果状态属于单个实例，只需要对象级互斥；如果多个实例共同访问 static 全局状态，则需要围绕 Class/static 共享资源同步。

实际项目怎么用

class SequenceService {
    private int localSeq;
    private static int globalSeq;

    public synchronized int nextLocal() {
        return ++localSeq;
    }

    public static synchronized int nextGlobal() {
        return ++globalSeq;
    }
}

AI补充/纠错

关键补充：同一个类里的 synchronized 实例方法和 static synchronized 方法并不会互相阻塞，因为锁对象分别是 this 和 Class 对象。

常见坑

  • 不要说“一个类只有一把 synchronized 锁”。锁对象是谁取决于 synchronized 作用目标。
  • 锁住错误对象会导致看似加锁但仍存在数据竞争。
  • 锁范围过大容易造成不必要串行化。
面试口述版：对象锁是某个实例对象上的 monitor，实例 synchronized 方法默认锁 this，不同实例之间通常不互斥；类锁是 Class 对象上的 monitor，static synchronized 方法锁的是 Xxx.class，因此同一类所有实例共享这把类锁。选择哪种取决于被保护的数据是实例级还是类级共享。

可能追问

两个不同实例的 synchronized 方法会互斥吗？static synchronized 和 synchronized(this) 会互斥吗？synchronized 的锁升级是什么？

⑤ 新题 4｜Agent 推理模式如何差异化设计与选择？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.6“Agent 推理模式、推理模式的差异化设计、推理模式的选择机制”｜PDF 第 5～6 页。

原资料内容

原资料按 Direct、CoT、ReAct、Plan-and-Solve、ToT、Reflexion 等模式比较推理深度、工具依赖、成本和容错，并给出决策逻辑。

模式适合任务主要代价
Direct简单事实/格式转换最便宜、能力有限
CoT 类分步推理无需外部工具的复杂分析更多推理 Token
ReAct边判断边查工具、环境动态变化多轮模型+工具调用
Plan-and-Solve步骤较明确的复杂长任务规划错误会影响后续
Reflexion结果需要额外审查、自修正再次调用模型，延迟更高
ToT / 搜索式需要探索多个候选路径成本最高、工程复杂

选择机制

任务简单？ → Direct
需要外部实时信息？ → ReAct / Tool Calling
步骤明确且较长？ → Plan-and-Solve
输出需要严格自检？ → Reflection/Reflexion
需要探索多条方案？ → ToT/搜索式

实际常见：Planning 做全局 + Tool/ReAct 做局部执行

Spring AI / Java 化

Spring AI 2.0 的 ToolCallingAdvisor 可以负责标准的递归 Tool Calling Loop，ToolCallingManager 执行工具。复杂 Planning、Reflection、ToT 并不是一个开关自动获得，通常要用 Java Service、状态对象、Advisor 或工作流显式组织。

// Tool Calling 基础
String answer = chatClient.prompt()
    .user("分析本月订单下降原因")
    .tools(orderTools)
    .call()
    .content();

// 更复杂模式通常要额外定义：
// planner -> plan -> executor -> validator -> retry/finish

AI补充/纠错

纠错：不要把“推理深度 Direct < CoT < ReAct < Plan-and-Solve < ToT”当成严格数学排序，它只是帮助选型的启发式比较。不同模型和任务下效果并不单调。
工程补充：生产系统不应依赖或要求暴露模型内部完整 Chain-of-Thought；面试时讲高层“分步推理/计划/行动/观察”即可。

常见坑

  • 能一次答完的问题硬套 Agent Loop，只会增加成本和延迟。
  • Tool 很多但描述模糊，会降低选择准确率。
  • Plan 不是不可变；复杂任务最好允许重规划。
  • Reflection 需要明确验收标准，否则容易“自我感觉良好”。
面试口述版：Agent 推理模式要按任务复杂度、是否依赖外部工具、步骤是否明确、准确性要求和成本预算选型。简单任务 Direct；需要动态工具交互用 ReAct/Tool Calling；长任务可先 Planning 再执行；高准确性场景增加 Reflection。Spring AI 可直接支持 Tool Calling Loop，而 Planning、Reflection 等通常要由 Java 业务层继续编排。

什么时候保留 Python？

如果需要自研模型推理、PyTorch/Transformers、复杂 OCR/CV、训练/微调，Python 服务非常合理。Java 与 Python 可以通过 HTTP/gRPC/MQ 解耦；但“用了 AI 就必须 FastAPI + LangChain”是不准确的。

常见坑

  • 把文件二进制直接塞关系型数据库而不考虑对象存储。
  • Embedding 同步堵住上传请求。
  • 只做向量相似度，不做 ACL 权限过滤。
  • 把所有文档全文塞给模型，成本和上下文都不可控。
  • 调用外部模型 API 却误以为应用服务器必须配 GPU。
面试口述版：AI 云盘可以采用 Spring Boot + Spring AI 作为主应用层，关系库保存业务元数据和权限，对象存储保存文件，Redis 做缓存/会话，MQ 异步处理解析和 Embedding，VectorStore 做语义检索，Spring AI 负责 RAG、Tool Calling 和模型接入。如果是自研模型或深度学习任务，再拆 Python 服务。核心不是堆技术，而是把文件、权限、异步处理、向量检索和模型能力分层。
