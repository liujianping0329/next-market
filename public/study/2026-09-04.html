复习 1｜? extends 与 ? super 怎么区分？

先回答：为什么 List<? extends Number> 主要用于读取，而 List<? super Integer> 适合写入 Integer？PECS 是什么？

答完后展开：纠错 + 口述版

纠错：? extends T 表示实际元素类型是 T 或其子类，读取时至少能当 T；但编译器不知道具体是哪种子类，所以不能安全写入具体 T。? super T 表示实际类型是 T 或其父类，因此写入 T 一定安全。

面试口述版：PECS 是 Producer Extends、Consumer Super。只从集合读取 T 时用 ? extends T；需要向集合写入 T 时用 ? super T。

复习 2｜Agent 工作模式怎么选？

先回答：Tool Calling、ReAct、Reflection、Plan-and-Solve、Multi-Agent、Human-in-the-Loop 分别适合什么任务？

答完后展开
简单工具查询      → Tool Calling
动态多步任务      → ReAct
结果需要自检      → Reflection
步骤较明确复杂任务 → Plan-and-Solve
专业角色分工      → Multi-Agent
高风险动作        → Human-in-the-Loop
口述版：Agent 模式应从最简单可用方案开始，复杂度越高，模型调用次数、延迟、状态管理和调试成本通常越高。

复习 3｜AI 项目的 PRD 为什么比普通 CRUD 更强调边界？

先回答：除了功能列表，一个生产级 AI PRD 至少还要写清哪些非功能与风险要求？

答完后展开

至少包含：模型能力边界、幻觉兜底、数据权限/隐私、延迟与成本、失败策略、人工接管条件、准确率/召回率/任务成功率等验收指标。对 SQL Agent 还应明确只读、白名单、超时、最大返回行数、审计和敏感字段规则。

间隔复习｜约 3 天前：capacity 和 size

先回答：ArrayList 的 capacity 与 size 分别是什么？HashMap 的 capacity 又是什么？

答完后展开

ArrayList capacity 是底层 elementData[] 长度，size 是实际元素个数；HashMap capacity 是 table[] 的长度，size 是实际键值对数量。

间隔复习｜约 3 天前：hashCode 与 equals

先回答：为什么 hashCode 相同不等于 equals 相同？

答完后展开

哈希冲突允许不同对象拥有相同 hashCode。HashMap 用 hash 缩小 bucket 范围，再用 equals 最终确认 Key；equals 为 true 时 hashCode 必须相同，反之不成立。

② 新题 1｜Java 反射技术和常见 API

原资料：《后端高频面试题大集合》JAVASE 核心，第 11 题“介绍 java 反射技术和常见的一些 API”｜PDF 第 9～11 页。原资料强调 Class、Constructor、Method、Field。

概念

反射就是程序在运行时获取类结构并动态创建对象、读取字段、调用方法的机制。核心入口是 Class<?>。

Class<UserService> clazz = UserService.class;
Method method = clazz.getDeclaredMethod("findById", Long.class);
Object result = method.invoke(userService, 1L);

原理

UserService.java
   ↓ javac
UserService.class
   ↓ JVM 加载
Class<UserService>
   ↓
Constructor / Method / Field 元数据
   ↓
运行时动态操作

为什么需要

框架无法在编译时写死所有业务类。Spring IOC、依赖注入、AOP、ORM、序列化等都需要在运行时读取类型、注解、构造器或方法元数据。

实际项目怎么用

你通常不会在 CRUD 里大量直接写反射，而是通过 Spring 间接使用：扫描 Bean、读取 @Component/@Autowired、创建对象、执行 AOP 代理、Mapper/序列化框架字段映射等。

AI补充/纠错

版本纠错 1：原资料列出的 Class.newInstance() 已从 Java 9 起标记 Deprecated。现代代码优先 clazz.getDeclaredConstructor().newInstance()。
版本纠错 2：Java 9+ 模块系统下，setAccessible(true) 不是“任何 private 都能无条件突破”；跨模块访问可能受 exports/opens 限制并抛出 InaccessibleObjectException。
Constructor<UserService> c = clazz.getDeclaredConstructor();
UserService service = c.newInstance();

常见坑

  • getMethods() 包含继承来的 public 方法；getDeclaredMethods() 只看当前类声明的方法，不要求 public。
  • 反射会降低类型检查的直观性，异常处理也更复杂，不应为了“高级”而滥用。
  • “反射一定非常慢”也过于绝对；框架常会缓存元数据，但直接调用仍通常比反射更简单、高效。
面试口述版：Java 反射是在运行时通过 Class 对象获取构造器、方法、字段等元数据，并动态创建对象或调用成员。Spring 的 Bean 扫描、依赖注入、AOP、ORM 等大量使用反射。现代 Java 中创建反射对象应优先使用 getDeclaredConstructor().newInstance()，而不是已经废弃的 Class.newInstance()。

③ 新题 2｜Java 自带注解与元注解

原资料：《后端高频面试题大集合》JAVASE 核心，第 12 题“有了解过哪些 java 自带的注解，什么是元注解”｜PDF 第 11～12 页。

概念

注解是附加在类、方法、字段等程序元素上的元数据，本身通常不直接执行逻辑，而是由编译器、框架或运行时工具解析。

常见标准注解作用
@Override声明重写父类/接口方法，编译器检查
@Deprecated标记 API 已废弃
@SuppressWarnings抑制指定编译警告

什么是元注解

元注解就是修饰注解的注解。

元注解作用
@Target允许注解出现在哪些程序元素
@RetentionSOURCE / CLASS / RUNTIME 保留策略
@Documented是否进入 Javadoc
@Inherited类上的注解是否可被子类继承
@Repeatable允许同一注解重复使用（Java 8+）

原理 / 为什么

@Retention(RUNTIME)
@Target(METHOD)
public @interface Audit {
    String value();
}

@Audit("refund")
public void refund() { ... }

// 运行时由 Spring/AOP/反射读取 @Audit 决定增强逻辑

AI补充/纠错

原资料有内部矛盾：资料一处写“Java 内置 4 种元注解”，但同页又列出了 @Repeatable。更准确地说，现代 Java 常见标准元注解至少包括 Target、Retention、Documented、Inherited，以及 Java 8 引入的 Repeatable。

实际项目怎么用

Spring 中 @Component、@Service、@Transactional、@RequestMapping 等都建立在注解元数据解析之上。你也可以用“自定义注解 + AOP”实现审计、权限、幂等、日志等横切能力。

常见坑

  • RetentionPolicy.RUNTIME 才能在运行时通过反射读取。
  • @Inherited 主要针对类级注解的继承，不等于方法注解自动继承。
  • 注解只是元数据，真正功能来自解析它的编译器/框架/代码。
面试口述版：注解是附加在代码元素上的元数据，常见标准注解有 Override、Deprecated、SuppressWarnings。元注解是用来定义注解行为的注解，比如 Target 决定可修饰位置，Retention 决定保留到源码、字节码还是运行时。Spring 大量通过运行时注解配合反射和 AOP 实现框架功能。

④ 新题 3｜静态代理与动态代理

原资料：《后端高频面试题大集合》JAVASE 核心，第 13 题“日常开发中有没有用过代理模式，说下动态和静态代理”｜PDF 第 13～14 页。

概念

代理模式是在客户端与真实对象之间加入代理对象，用来控制访问或在调用前后增加横切逻辑。

Client → Proxy → Target
             ↑
       日志 / 事务 / 权限 / 缓存

静态代理

代理类在运行前已经存在，通常代理类与目标类实现同一接口，代理持有目标对象。

class OrderServiceProxy implements OrderService {
    private final OrderService target;
    public void create() {
        logBefore();
        target.create();
        logAfter();
    }
}

动态代理

运行时生成代理，不需要为每个目标类手写完整代理类。JDK 动态代理基于接口与 InvocationHandler；类代理通常可使用 CGLIB 一类字节码生成方案。

OrderService proxy = (OrderService) Proxy.newProxyInstance(
    OrderService.class.getClassLoader(),
    new Class[]{OrderService.class},
    (p, method, args) -> {
        System.out.println("before");
        Object result = method.invoke(target, args);
        System.out.println("after");
        return result;
    });

为什么

代理把事务、日志、权限、监控等逻辑从业务类中抽离，符合关注点分离和开闭原则。

实际项目怎么用｜Spring AOP

@Transactional
public void pay() { ... }

调用者
  ↓
Spring Proxy
  ↓ 开事务
Target.pay()
  ↓
提交 / 回滚

Spring AOP 的核心实现就与代理机制密切相关：能够使用接口代理时可采用 JDK 动态代理；需要代理具体类时可采用基于子类的代理方式。

AI补充/纠错

纠错：把“动态代理 = 反射”说成完全等号不够准确。JDK 动态代理的 InvocationHandler 确实大量使用反射 Method 调用；CGLIB 则核心是运行时生成目标类的子类字节码。二者都属于运行时代理，但实现机制不同。

常见坑

  • JDK 动态代理要求从接口维度代理。
  • 基于子类的代理无法覆盖 final 类/final 方法等不可继承/重写结构。
  • Spring AOP 中同一个类内部的 this.method() 自调用可能绕过代理，因此 @Transactional 等增强可能不生效。
面试口述版：静态代理的代理类在运行前已经确定，优点直观但类多时维护成本高；动态代理在运行时创建代理对象，JDK 动态代理基于接口和 InvocationHandler，CGLIB 类方案通过生成目标类子类实现。Spring AOP 会利用代理把事务、日志、权限等横切逻辑与业务代码解耦。

可能追问

JDK Proxy 和 CGLIB 区别？为什么 @Transactional 自调用失效？AOP 为什么需要代理？final 方法为什么难以被类代理增强？

⑤ 新题 4｜Agent 的设计范式有哪些？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.5“了解过 Agent 的设计范式吗？了解其他的 Agent 范式吗？”｜PDF 第 4～5 页。原资料列出 ReAct、Reflection、Tool Use、Planning、Multi-Agent Collaboration、Sequential Workflow、Human-in-the-Loop，并补充 LATS、Voyager、Generative Agents、Self-Discover、RAISE。

概念

昨天的“工作模式”偏一个 Agent 怎么运行；今天的“设计范式”更偏整个 Agent 系统采用什么架构方法组织推理、工具、工作流和协作。

范式核心适用
ReAct推理与行动交替动态、多步任务
ReflectionActor 输出后由 Critic 评估并迭代高准确性任务
Tool Use模型选择和组合外部能力DB/API/搜索/文件
Planning先生成全局计划再执行复杂但可拆解任务
Multi-Agent多个专业 Agent 分工跨专业复杂任务
Sequential Workflow预定义固定步骤流水线确定性业务流程
Human-in-the-Loop关键动作等待人工决定金融/写库/审批等高风险操作

原理 / 为什么

Agent 并不是“自主程度越高越好”。生产系统通常需要在确定性、成本、延迟、可解释性与自主性之间做权衡。

固定流程多、规则清晰
→ Sequential Workflow

环境变化大、需要边查边判断
→ ReAct

高风险动作
→ Human-in-the-Loop

复杂跨角色任务
→ Multi-Agent（确认真的有必要再上）

Java / Spring AI 化

AI补充/纠错：这些是架构范式，不应假装 Spring AI 每个都有一个同名“一键模块”。Spring AI 2.0 当前明确提供 Tool Calling Loop（ChatClient + ToolCallingAdvisor + ToolCallingManager）作为 agentic 基础；Planning、Reflection、Multi-Agent、审批等更高层范式通常由 Spring Service、状态机、工作流或自定义 Advisor/编排实现。

// Tool Use 基础
chatClient.prompt()
    .user(task)
    .tools(databaseTools, mailTools)
    .call()
    .content();

// 高风险写操作
if (plan.requiresWrite()) {
    approvalService.requireHumanApproval(plan);
}
Spring AI 2.0 当前版本确认：ToolCallingAdvisor 是递归 Advisor，负责工具执行生命周期；DefaultChatClient 会自动注册它，ToolCallingManager 执行 Tool，直到模型返回不含 Tool Call 的响应。它是 Agentic AI 的基础，但不是全部 Agent 范式。

常见坑

  • 把“范式名称”背成框架 API 名。
  • 为了炫技过早引入 Multi-Agent，导致成本、状态一致性和调试复杂度暴涨。
  • 固定确定性流程也全交给 LLM 自由规划，降低可靠性。
面试口述版：Agent 常见设计范式包括 ReAct、Reflection、Tool Use、Planning、Multi-Agent、Sequential Workflow 和 Human-in-the-Loop。选型核心不是越智能越好，而是根据任务确定性、风险、成本和动态性选择。Spring AI 能提供 Tool Calling、Memory、RAG、Advisor 等基础能力，更高层 Planning、Reflection 或 Multi-Agent 通常还要由 Java 业务层编排。

可能追问

工作模式和设计范式区别？Sequential Workflow 为什么有时比 ReAct 更可靠？Multi-Agent 的通信和状态怎么管理？Human-in-the-Loop 应放在哪个节点？

⑥ 新题 5｜AI 智能云盘对硬件资源和部署有什么要求？

原资料：《AI大模型面试题-基础篇》第 5 题“在 AI 智能化云盘项目中，对硬件资源和部署有什么特殊要求？”｜PDF 第 4～5 页。原资料强调模型参数规模、算力、开发/生产差异、云算力和成本控制。

概念

先区分两种完全不同的部署路线：

路线你的应用服务器主要算力压力
调用外部 LLM API普通 CPU/内存即可承担 Spring Boot、RAG、业务逻辑模型 GPU 在供应商侧
本地/私有化部署模型除业务服务外，还要运行推理服务GPU 显存、吞吐、并发成为核心约束

原理 / 为什么

LLM 的参数、KV Cache、上下文长度和并发会共同消耗显存。模型越大、上下文越长、同时请求越多，推理资源成本通常越高；量化可以降低显存，但可能影响精度、速度或硬件适配。

AI补充/纠错｜对 Spring AI 项目尤其重要

原资料容易让人误解成“做 AI 应用一定要自己准备 GPU”。这不对。如果你的 Spring Boot + Spring AI 主要调用 OpenAI、Azure、通义、Gemini 等外部模型 API，本地服务器并不需要为 LLM 推理配 GPU；你主要关注 API 延迟、限流、成本、网络稳定性与降级。GPU 主要在自托管模型、Embedding/Reranker 本地推理、训练/微调时才成为直接资源问题。

实际项目怎么用

方案 A：外部模型 API
Next.js
  ↓
Spring Boot + Spring AI
  ├─ DB / Redis
  ├─ VectorStore
  └─ HTTPS → 外部 LLM Provider

方案 B：私有模型
Spring Boot + Spring AI
  ↓
内部 Model Serving
  ↓
GPU Server / Cluster

AI 云盘还要单独规划：对象存储（MinIO/OSS/S3）、文档解析任务、Embedding 批处理、Vector DB、缓存、异步队列，以及日志/监控。大文件解析和向量化最好异步化，避免 Web 请求长期占用线程。

成本控制

  • 开发环境可用小模型/API 小额度，不要照搬生产规格。
  • 外部 API：关注 Token、缓存、上下文裁剪、模型分级路由。
  • 自托管：关注 GPU 利用率、量化、批处理、并发和弹性伸缩。
  • RAG：Embedding 不必每次重复生成，文档变更时增量更新。

常见坑

  • 把“应用开发服务器配置”和“模型推理服务器配置”混为一谈。
  • 只算 GPU，不算向量库、对象存储、网络和文档处理成本。
  • 上传文件后同步完成解析+Embedding，导致接口超时。
面试口述版：AI 项目的硬件要求首先取决于模型是调用外部 API 还是私有化部署。调用 API 时，Spring Boot 应用本身通常不需要 GPU，重点是网络、限流、Token 成本和可靠性；如果自托管模型，则需要根据模型大小、量化、上下文和并发评估 GPU 显存与吞吐。AI 云盘还要规划对象存储、文档解析、Embedding、VectorStore 和异步任务资源，开发与生产应采用不同规格并持续做成本优化。
